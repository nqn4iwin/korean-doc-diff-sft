# 01. 공공데이터 활용 사전검토 데이터

공공데이터를 수집·가공·모델 학습·서비스 개발에 사용할 때 확인해야 하는 법령,
이용조건, 개인정보와 저작권 관련 자료를 수집하고, 사전검토용 데이터셋을 실제로
구축할 수 있는지 검증한다.

이 디렉터리의 목표는 모델이나 챗봇 서비스를 개발하는 것이 아니다. 공식 원천을
재현 가능하게 수집하고, 출처와 버전을 보존하며, 다음 형태의 SFT 후보를 얼마나
만들 수 있는지 확인하는 데 집중한다.

```text
공공데이터와 사용 상황
→ 1차 분류
→ 반드시 확인할 사항
→ 추가 질문과 실무 조치
→ 판단 근거
```

법률 자문이나 최종적인 사용 허가를 자동화하지 않는다. 공식 근거만으로 결론을
확정할 수 없는 경우에는 `추가 확인 필요` 또는 `담당자 검토 필요`로 분리한다.

## 범위와 비목표

이 프로젝트의 성공 기준은 외부 원천을 전부 복제하거나 모든 raw를 학습데이터로
변환하는 것이 아니다. 한 달 안에 다음 질문에 근거를 갖고 답하는 것이 목표다.

- 목표에 맞는 공공데이터·법령·안내서 raw를 재현 가능하게 수집할 수 있는가
- 목록 중 실제 사전검토 사례에 유용한 대상을 규칙과 표본 검수로 선별할 수 있는가
- 선별된 raw에서 인용 가능한 근거와 SFT 후보를 안정적으로 구조화할 수 있는가
- 자동화 가능한 부분과 법률·업무 담당자 검수가 필요한 부분의 비율은 얼마인가

공공데이터포털 전체 목록의 전수 수집, 전체 법령 말뭉치 구축, 모든 raw의 SFT 변환,
법률적 적합성의 자동 확정은 이번 범위에서 제외한다.

## 확보한 데이터 원천

현재 연동 대상으로 확보한 외부 원천은 두 개다. 두 원천은 같은 정보를 제공하는
것이 아니라 각각 `판단 근거`와 `검토 대상` 역할을 한다.

### 1. 국가법령정보 공동활용 Open API

- 제공처: 법제처 국가법령정보센터
- 주소: `https://open.law.go.kr`
- 인증방식: 사용자가 직접 지정하고 승인받은 OC
- 이 프로젝트에서의 역할: **판단 근거 데이터**

신청한 주요 범위는 다음과 같다.

- 대한민국 현행법령
- 현행 행정규칙
- 법령해석례
- 개인정보보호위원회·행정안전부·문화체육관광부의 부처별 법령해석
- 판례·행정심판례·결정례
- 법령용어, 일상용어-법령용어 및 조문-법령용어 연계정보

수집하는 이유는 단순히 법령 전문을 모델에 학습시키기 위해서가 아니다. 답변에서
실제로 존재하는 법령명·조문·시행일을 인용하고, 특정 상황에 어떤 확인 절차가
필요한지 설명할 수 있는 RAG 근거를 구축하기 위해서다.

예상 용도는 다음과 같다.

- 공공데이터법·개인정보 보호법·저작권법의 현행 조문 수집
- 법률-시행령-행정규칙 관계 연결
- 시행일·공포일·개정이력을 이용한 최신 근거 판별
- 법령해석례·판례·결정례에서 사실관계-판단-근거 후보 추출
- 일상적인 질문을 법령용어와 관련 조문에 연결

2026년 7월 28일에 현행법령 검색과 MST 기반 본문 조회를 검증했다. 검색 응답에서
다음 필드를 확인했다.

- 법령일련번호와 법령 ID
- 법령명과 법령 구분
- 소관부처
- 공포일자와 시행일자
- 제·개정 구분
- 법령 본문 조회에 사용할 상세 링크

본문 응답에서는 기본정보, 조문, 부칙, 개정문과 제·개정이유를 확인했다. 따라서
현행 조문과 버전 근거를 수집할 수 있다는 점은 확인했으며, 다음 검증 대상은
조·항·호 파싱과 법령해석례·판례·결정례의 사례 구조다.

법령 API는 상세 링크 안에 OC를 포함하여 반환하므로 저장 전에 해당 값만
`<redacted>`로 마스킹한다.

### 2. 공공데이터포털 목록조회서비스

- 제공처: 공공데이터활용지원센터
- 주소: `https://www.data.go.kr`
- 서비스: `공공데이터활용지원센터_목록조회서비스`
- 인증방식: 공공데이터포털 일반 인증키
- 이 프로젝트에서의 역할: **검토 대상 데이터**

조회 대상은 다음 네 종류다.

- 전체 데이터셋
- 파일 데이터
- Open API
- 표준 데이터셋

이 원천은 실제 사용자가 검토하려는 공공데이터의 이름, 제공기관, 설명과 데이터
유형 등의 메타데이터를 확보하기 위해 수집한다. 이후 개별 상세정보에서 이용조건,
비용, 제3자 권리, 개인정보 가능성과 유의사항을 얼마나 얻을 수 있는지 확인한다.

예상 용도는 다음과 같다.

- 실제 데이터셋을 기반으로 한 검토 시나리오 생성
- 제공기관·데이터 유형·이용조건별 표본 추출
- 상업적 이용, 변경, 출처표시 및 재배포 조건 정규화
- 법적 근거가 필요한 항목과 단순 이용조건 확인 항목 분리
- 데이터 목록 및 이용조건 변경 추적

활용신청 승인과 일반 인증키 발급은 완료됐다. 2026년 7월 28일에 전체 데이터셋
목록을 1건 요청하는 최초 연동 테스트도 완료했다. 응답에서 다음 필드를 확인했다.

- 데이터셋 ID, 제목, 설명과 키워드
- 제공기관 코드와 이름
- 데이터 유형과 분류
- 등록일·수정일, 삭제 여부와 등록 상태
- 상세 페이지 URL
- 제공 범위 코드와 소유권 근거

목록 응답은 데이터셋 식별과 표본 추출에는 사용할 수 있다. 다만 최초 표본의
`ownership_grounds`는 비어 있었고 `providing_scope`는 코드값만 반환되므로,
상업적 이용·변경·출처표시·재배포 등의 구체적인 이용조건은 개별 상세정보에서
보완할 수 있는지 추가로 확인해야 한다.

## 두 원천의 결합 방식

```text
공공데이터포털
  실제 데이터셋과 이용조건
          │
          ▼
  사용 목적·외부 전송 여부를 결합한 검토 시나리오
          │
          ▼
국가법령정보
  관련 법령·행정규칙·해석례·판례 검색
          │
          ▼
  판단 근거 + 확인사항 + 추가 질문 + 담당자 검토 여부
```

공공데이터포털 정보만으로 개인정보나 외부 전송의 적법성을 확정하지 않는다.
반대로 법령 원문만으로는 구체적인 SFT 상황을 충분히 만들기 어렵다. 두 원천을
연결해야 실제 데이터에 근거한 질문과 공식 근거가 있는 답변 후보를 만들 수 있다.

## 보존된 전수 인벤토리 계획

초기에는 두 공식 원천의 전체 목록을 기준 인벤토리로 확보할 계획이었다. 실제
호출량을 확인한 뒤 2026년 7월 29일 전수 목록 수집을 중단하고 키워드 수율
탐색으로 전환했다. 아래 내용은 당시 설계와 보존된 체크포인트를 설명하며,
현재 실행 전략은 뒤의 `키워드 수율 탐색으로 전환` 절을 따른다.

```text
공공데이터포털·Open Law 전체 목록 인벤토리
→ 식별자 기준 중복 제거와 공식 관계 확장
→ 규칙 기반 관련성 분류
→ 상세 판독 약 100건(priority 60 + 경계 20 + 대조군 20)
→ 개발용·최종 제외 집합 누락 감사 각 60~100건
→ RAG 근거와 SFT 후보
```

### 1. 전체 목록 인벤토리

공공데이터포털의 `dataset`·파일·Open API·표준 데이터 목록과 Open Law의 현행
법령·행정규칙 목록을 전수 확보한다. 목록의 식별자, 제공기관 또는 소관부처,
유형, 수정일 또는 시행일과 상세 링크를 기준 모집단으로 보존한다.

공공데이터포털 네 목록은 2026년 7월 28일 기준 응답 행 합계가 332,120건이며
목록 사이와 `open-data-list` 내부에 중복이 있다. 전수 목록은 고유 학습 후보 수가
아니라 중복 제거와 제외 집합 감사가 가능한 기준 인벤토리다.

### 2. 관련성 분류

제목·설명·키워드·기관·제공 범위 코드와 상세정보 존재 여부를 이용해 다음 세
등급으로 분리한다.

- `priority`: 개인정보, 저작권, 제3자 권리, 상업 이용, 변경·재배포, AI 학습,
  외부 전송과 직접 관련되거나 이용조건이 불명확한 데이터
- `sample`: 위험 신호는 약하지만 데이터 유형·기관·이용조건의 대표성을 위해
  남겨야 하는 데이터
- `exclude`: 삭제·중복 데이터, 목적과 무관한 자료, 상세정보가 전혀 없고 보완
  경로도 없는 데이터

초기 분류는 재현 가능한 규칙으로 수행하고, 각 등급의 표본을 사람이 확인해
오분류율을 기록한다. LLM 분류를 사용하더라도 단독 정답으로 간주하지 않는다.

### 3. 상세정보와 근거 확장

상세 판독 약 100건은 `priority` 60건, 판단이 애매한 경계 사례 20건, 위험 신호가
없는 대조군 20건을 기본으로 하며 데이터 유형·기관·주제가 한쪽에 쏠리지 않도록
층화한다.

Open Law는 전체 목록을 확보하되 전체 현행 본문은 이번 파일럿에서 받지 않는다.
공공데이터법·개인정보 보호법·저작권법으로 사전에 고정한 기준 법령 집합과 공식
상하위·위임·인용 관계로 연결되는 시행령·시행규칙·행정규칙의 현행 본문을
우선한다. 공공누리와 개인정보보호위원회 안내서는 법령 원문과 개별 데이터
이용조건 사이의 실무 지침을 보완한다.

### 4. 수집 중단 기준

다음 조건을 만족하면 목록 수집을 종료하고 구조화·검증에 시간을 사용한다.

- 두 원천의 승인된 전체 목록 페이지를 수집하고 파일·체크섬 무결성을 확인
- 사전에 고정한 기준 법령 집합의 검색 재현율 100%
- 공식 관계에서 처리되지 않은 대상 0건 또는 승인 제한 등 사유 기록
- 개발용 제외 감사 후 별도의 최종 제외 집합 60~100건에서 중대한 누락 0건
- 모든 포함·제외 항목에 재현 가능한 사유 기록

제외 집합 100건에서 누락이 0건이어도 전체 누락률이 0이라는 뜻은 아니다. 단순
무작위 표본 가정에서 미탐률의 95% 상한은 약 3%이므로 표본 수와 발견 건수를
결과에 함께 기록한다.

## 한 달 작업 범위

근무일 약 20일, 하루 8시간의 총 160시간 중 기준 인벤토리 구축과 수집 범위
확정에는 사람 투입시간 기준 30~40시간만 배정한다.

- 공공데이터포털 네 목록 메타데이터: 승인된 전체 페이지
- Open Law 현행 법령·행정규칙: 승인된 전체 목록
- 공공데이터 상세 판독: 약 100건
- 법령 본문: 기준 법령과 공식 관계로 확장된 후보
- 개발용 제외 감사: 60~100건
- 독립적인 최종 제외 감사: 60~100건
- 나머지 시간: 상세 판독, SFT 후보 제작·검수, RAG 구축, 학습 실행과 평가

이번 SFT의 목표는 범용 법률 판단 성능을 주장하는 것이 아니라 Gold·Silver·
Synthetic을 분리한 생성·검수·학습 파이프라인과 출력 형식의 가능성을 검증하는
것이다.

## 디렉터리 구조

코드와 문서는 이 디렉터리에 두고, 원본·중간·가공 데이터는 저장소 루트의 `data/`
아래에 단계별로 분리한다.

```text
01_public_data_review/
├── README.md
├── config.example.env
├── crawlers/
│   ├── _common.py
│   ├── law.py
│   ├── data_portal.py
│   ├── timed_collection.py
│   ├── pilot_collection.py
│   ├── open_law_yield_pilot.py
│   └── sanitize_law_snapshots.py
├── parsers/                       # 예정: 원천별 응답 구조화
│   ├── law.py
│   ├── data_portal.py
│   └── case.py
├── schemas/                       # 예정: manifest·근거·SFT 스키마
```

## 데이터 처리 단계

```text
API 호출
→ raw 응답 저장
→ manifest 기록
→ 원천별 parser
→ 공통 필드 정규화
→ RAG 근거 청크 및 SFT 후보 생성
→ 규칙 검사와 표본 수동 검수
→ processed JSONL 및 가능성 보고서
```

- `raw`: API가 반환한 수집 응답. 인증값만 마스킹하고 의미 내용은 변경하지 않는다.
- `interim`: 조·항·호, 이용조건, 사실관계와 판단 등을 공통 구조로 변환한 결과다.
- `processed`: 출처와 근거 검증을 통과한 RAG 또는 SFT용 JSONL이다.
- `manifest`: 원천, endpoint, 비밀정보가 아닌 요청조건, 수집시각, 경로, 크기와
  SHA-256을 기록한다.

## 시간제 자동수집

기본 설정으로 약 60분 동안 요청 사이에 90~105초의 간격을 두고 두 API를
번갈아 호출한다.

```powershell
python .\01_public_data_review\crawlers\timed_collection.py
```

자동수집기는 다음 순서로 표본을 넓힌다.

- Open Law에서 공공데이터법·개인정보 보호법·저작권법을 검색
- 검색 결과의 MST를 큐에 넣고 법령 본문 수집
- 공공데이터포털의 전체·파일·Open API·표준 목록을 순환
- 포털 요청당 20건씩 받고 원천별 다음 페이지로 이동

기본 간격에서는 1시간에 약 35~40회의 요청이 발생한다. 진행 상태는 Git에서
제외되는 다음 파일에 저장하므로 중단한 뒤 같은 명령을 실행하면 이어서 수집한다.
이 실행기는 전수 수집기가 아니라 초기 표본 확보용이며, 목표 표본 수와 중단 기준을
충족하면 목록 호출을 종료한다.

```text
data/01_public_data_review/state/timed_collection.json
```

API를 호출하지 않고 다음 작업과 체크포인트만 확인할 수도 있다.

```powershell
python .\01_public_data_review\crawlers\timed_collection.py --dry-run
```

실행 시간과 간격은 조정할 수 있지만 차단 위험을 줄이기 위해 기본값보다 짧게
설정하지 않는 것을 권장한다.

```powershell
python .\01_public_data_review\crawlers\timed_collection.py `
  --duration-minutes 120 `
  --interval-seconds 120 `
  --jitter-seconds 30
```

## 파일럿 전체 목록 수집

`pilot_collection.py`는 표본용 수집기와 별도의 체크포인트를 사용해 목표가
완료될 때까지 다음 작업을 반복한다.

- 공공데이터포털 네 목록을 요청당 1,000행으로 전수 수집
- Open Law 현행 법령 목록을 요청당 100행으로 전수 수집
- 승인된 경우 행정규칙 전체 목록 수집
- 기준 법령 검색 결과의 현행 본문과 공식 위임·인용 관계 수집
- 포털 목록 완료 후 `priority` 60·경계 20·대조군 20의 상세 판독 표본 생성
- 표본 중 공식 catalog JSON 주소가 있는 항목의 상세 메타데이터 수집
- 일시 오류 시 같은 페이지를 유지하고 재시도
- 각 snapshot의 출처·요청조건·수집시각·크기·SHA-256 기록

실행 전에는 1,000행 응답과 각 Open Law 서비스의 승인 상태를 한 번씩 점검한다.
진행 상태, 로그와 경고는 다음 위치에 남는다.

```text
data/01_public_data_review/state/pilot_collection.json
data/01_public_data_review/state/pilot_collection.log
data/01_public_data_review/interim/pilot_detail_sample.jsonl
01_public_data_review/WARNING.md
```

목록에 catalog JSON 주소가 없는 표본은 자동으로 임의 URL을 만들지 않고 수동
판독 대상으로 기록한다. 실제 데이터 파일이나 개별 Open API 응답은 크기·이용조건·
개인정보 가능성을 먼저 확인해야 하므로 이 실행기가 자동 다운로드하지 않는다.

상태만 확인할 때는 API를 호출하지 않는다.

```powershell
python .\01_public_data_review\crawlers\pilot_collection.py --status
```

백그라운드 수집은 다음 명령과 같은 설정으로 실행한다. 체크포인트가 있으므로
프로세스가 중단된 뒤 같은 명령을 실행해도 완료되지 않은 페이지부터 재개한다.

```powershell
python .\01_public_data_review\crawlers\pilot_collection.py `
  --interval-seconds 90 `
  --jitter-seconds 15
```


일반 문서 원천의 각 검색은 최대 100개 결과를 받아 검색어당 새 후보 10개,
원천당 최대 100개 고유 후보를 만든다. 지능형 API는 각 검색어를 법령 조문과
행정규칙 조문으로 나누어 호출한다. 지능형 검색은 조문 본문 발견률, 연관법령은
관련 조문 확장률을 별도 지표로 기록한다. 총 130개 검색 요청 뒤 20시간 요청
예산에서 일반 문서 본문은 원천당 65개를 우선 확보한다. 결과가 적은 원천에서
남는 본문 요청은 후보가 많은 원천에
재배분하며, 작은 원천은 공식 검색 결과 전부가 100건 미만일 수 있음을 그대로
보고한다. 따라서 100건은 존재하지 않는 문서를 채우는 할당량이 아니라 탐색 상한이다.

수집기는 검색과 본문을 번갈아 수행하고 원천별 완료 본문 수가 낮은 곳부터
선택한다. 이 방식은 한 원천의 무관한 문서를 오래 순차 수집하는 것을 막으면서,
중단 시 체크포인트부터 재개한다.

```powershell
python .\01_public_data_review\crawlers\open_law_yield_pilot.py `
  --duration-hours 20 `
  --interval-seconds 90 `
  --jitter-seconds 15
```

상태 확인은 API를 호출하지 않는다.

```powershell
python .\01_public_data_review\crawlers\open_law_yield_pilot.py --status
```

결과 위치는 다음과 같다.

```text
data/01_public_data_review/state/open_law_yield_pilot.json
data/01_public_data_review/state/open_law_yield_pilot.log
data/01_public_data_review/interim/open_law_yield_index.jsonl
data/01_public_data_review/reports/open_law_yield_pilot.md
01_public_data_review/WARNING.md
```

중간 보고서의 `고신호 본문`은 개인정보·저작권·제3자·재배포·국외 이전·AI 등
고위험 관련어가 둘 이상 나타난 문서다. 이는 자동 정답 라벨이 아니라 원천별
수율을 비교하기 위한 휴리스틱이다. 탐색 종료 후에는 본문 수, 고신호 비율,
사실관계·판단·조치 구조의 충실도를 함께 보고 후속 본수집 원천을 선택한다.
지능형 API는 독립적인 법적 사례 본문이 아니라 검색·확장 도구이므로 일반 원천과
동일한 Gold 후보 수로 합산하지 않는다.

### 2026년 7월 30일 1차 탐색 결과

10개 키워드의 검색 조합 130개를 모두 완료했다. 9개 문서 원천에서 고유 후보
662건을 찾고 본문 590건을 수집했으며, 지능형 검색과 연관법령에서는 고유 결과를
각각 100건 확보했다. API 요청은 성공 720회, 실패 3회였고 일시 실패 대상은
재시도하여 목표 본문 수에 포함했다.

`고신호 본문`은 관련어가 2개 이상 나타난 문서 수일 뿐 최종 적합 판정이 아니다.

사례와 법령해석례의 저작권·정보 제공 질의가 직접 활용 가능했다. 반면 넓은
키워드로 검색된 판례·행정심판례에는 무관 문서도 포함되어 본수집 전 사람이
원천별 검색 규칙을 다시 정해야 한다.

## 데이터 등급 원칙

- `gold`: 공식 질의응답·결정례에서 사실관계와 판단을 직접 추출하고 검증
- `silver`: 데이터의 명시적 이용조건이나 규칙으로 확인사항 생성
- `synthetic`: 실제 데이터셋에 가상의 사용 목적·외부 전송 조건 등을 결합
- `human_review_required`: 공식 근거만으로 결론을 확정할 수 없음

법률 원문이나 LLM이 생성한 판단을 그 자체로 Gold 라벨로 간주하지 않는다.

## 보안 및 재현성

- `.env`와 `data/`는 Git에 커밋하지 않는다.
- API가 응답에 인증값을 포함하면 저장 전에 `<redacted>`로 마스킹한다.
- 오류 메시지에 인증값이 포함되지 않도록 전체 요청 URL을 출력하지 않는다.
- 공식 문서의 출처·시행일·개정일과 수집일을 함께 보존한다.
- 동일 요청을 다시 수행해 변경 여부를 비교할 수 있도록 체크섬을 기록한다.
