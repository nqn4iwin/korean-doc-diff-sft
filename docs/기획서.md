## TL;DR

- 본 프로젝트는 조달청의 IT 분야 입찰문서(사전규격, 입찰공고)를 읽고, 요구사항과 그 변화가 사업 수행에 갖는 의미를 근거와 함께 설명하는 SLM을 만드는 것입니다.
- 주 목표는 한 과제에 대한 2개 문서의 차이가 **요구 수준, 책임, 검증 조건, 발주기관의 우선순위 등의 측면에서 어떻게 달라졌는지**를 작은 모델이 해석해내는 데 있습니다.

## 1. 문제정의와 프로젝트 범위

### 1.1 문제정의

기존 RFP 분석 도구는 한 개의 문서에서 요구사항과 메타데이터를 추출하고, 질의응답·Compliance Matrix·제안서 초안 작성을 지원하는 데 초점을 둔다. 그러나 동일 사업의 사전규격과 최종 입찰공고를 연결해 요구사항이 어떻게 달라졌는지 찾고, 그 변화가 구현 범위·사업자 책임·검증 조건에 갖는 의미까지 설명하는 기능은 확인하기 어렵다.

조달 IT 사업 문서는 분량이 길고 요구사항이 표·목록·여러 장에 흩어져 있다. 사용자는 두 문서를 직접 대조하면서 다음 내용을 판단해야 한다.

- 어떤 요구사항이 추가·삭제·강화·완화되었는가?
- 수치·기한·수행 주체·검증 방식은 어떻게 달라졌는가?
- 변경으로 인해 구현 부담과 사업 리스크가 어떻게 변하는가?
- 여러 변경을 종합했을 때 발주기관이 새롭게 강조한 것은 무엇인가?

문제는 **변경 근거를 요구사항 단위로 연결하고, 확인된 사실과 가능한 해석을 구분해 설명해 주는 도구가 없다는 점**이다.

따라서 본 프로젝트는 두 문서에서 변경된 정보를 통해 SFT한 작은 모델이 두 문서의 요구사항을 토대로 달라진 내용을 해석해내는 것이 목표이다.

### 1.2 제공 기능

Case A. 단일 문서를 입력하면 다음 정보를 제공한다.
   - **핵심 요구사항:** 주요 기술 영역과 요구사항을 요약
   - **요구사항 구조:** 주체·의무·조건·제약·검증기준으로 구분
   - **실행 안내:** 구현 고려사항, 잠재 리스크와 확인 질문 제시

Case B. 동일 사업의 사전규격과 입찰공고를 입력하면 다음 정보를 추가로 제공한다.
   - **변경 내용:** 대응 요구사항과 추가·삭제·수정 내용 제시
   - **변화 유형:** 강화·완화·책임 이동 등 의미 변화 분류
   - **종합 분석:** 발주기관의 강조사항과 제안 시 고려사항 정리

### 1.3 범위와 비범위

| 포함 범위                     | 제외/보류 범위                 |
| ------------------------- | ------------------------ |
| IT 분야 사전규격·입찰공고 수집 및 연결   | 전 산업군 범용화                |
| HWP/PDF의 구조화 및 요구사항 단위 추출 | 범용 문서 파서 자체의 신규 연구       |
| 요구사항 정렬, Diff, 변화 유형 분류   | 발주기관의 실제 내적 의도 확정        |
| 근거 기반 변화 해석 모델 SFT        | 제안서 전체 자동 작성 및 낙찰 가능성 예측 |
| 자동평가 중심의 비교 실험            | 초기 단계의 대규모 RL 학습         |

## 2. 유사서비스 및 선행연구

### 2.1 유사서비스와 차별점

공개된 RFP 서비스는 주로 한 개 문서에서 요구사항을 추출하거나 질의응답·제안서 작성을 지원한다.

- **[RFP Accelerator](https://github.com/DanGiannone1/rfp_accelerator)**
  - 설명: 문서 처리, 요구사항 추출, RFP 질의응답과 응답서 작성을 지원한다.
  - 한계: 단일 RFP 활용이 중심이며 사전규격과 최종 공고의 변화 의미는 분석하지 않는다.
- **[IBM Procurement AI Agents](https://www.ibm.com/kr-ko/products/watsonx-orchestrate/procurement)**
  - 설명: RFP 초안, 공급업체 추천과 계약 워크플로를 지원한다.
  - 한계: 구매 업무 자동화가 중심이며 요구사항 변경의 근거와 영향을 설명하는 도구는 아니다.
- **[Semi-Structured Tender Document RAG](https://arxiv.org/abs/2410.09077)**
  - 설명: 반구조화된 조달문서를 검색해 전문 Tender 문서를 생성한다.
  - 한계: 문서 생성이 중심이며 Draft-to-Final 요구사항 비교를 다루지 않는다.

따라서 본 프로젝트는 **동일 사업의 두 문서를 연결하고, 요구사항 변경의 유형·영향·발주기관의 강조 변화를 근거와 함께 설명한다는 점**에서 차별화된다.

### 2.2 참고 선행연구

#### 요구사항 분석과 추적성

- **[LLM-based Requirements QA](https://arxiv.org/abs/2408.10886), [INCOSE 요구사항 작성 지침](https://www.incose.org/docs/default-source/working-groups/requirements-wg/guidetowritingrequirements/incose_rwg_gtwr_v4_summary_sheet.pdf)**
  - 설명: 명확성·완전성·검증 가능성 등 요구사항의 품질 기준을 제시한다.
  - 적용: 단일 문서의 요구사항 품질 점검 기준으로 사용한다.
- **[NLP for Requirements Traceability](https://arxiv.org/abs/2405.10845)**
  - 설명: 요구사항과 관련 산출물 사이의 대응 링크를 찾고 평가하는 방법을 다룬다.
  - 적용: 사전규격과 입찰공고 요구사항의 1:1·1:N·N:1 관계를 구성하는 데 활용한다.
- **[NLI in Requirements Engineering](https://arxiv.org/abs/2405.05135)**
  - 설명: 요구사항 쌍의 함의·모순·중립 관계를 판별한다.
  - 적용: 요구사항 정렬과 생성된 해석의 근거 정합성을 검사하는 보조 방법으로 사용한다.

#### 추론 과정 Distillation

- **[Distilling Step-by-Step](https://aclanthology.org/2023.findings-acl.507/)**
  - 설명: Teacher가 생성한 Rationale을 정답과 함께 추가 감독 신호로 사용해 작은 모델을 학습한다.
  - 적용: 변경 근거·변화 유형·영향으로 구성된 분석 과정을 Instruction Data에 포함하는 근거로 사용한다.
- **[Orca](https://www.microsoft.com/en-us/research/publication/orca-progressive-learning-from-complex-explanation-traces-of-gpt-4/)**
  - 설명: 큰 모델의 설명 Trace와 복잡한 지시를 학습해 작은 모델의 추론 성능을 높인다.
  - 적용: 자유형 장문 사고과정보다 검증 가능한 구조화 분석 레코드를 학습하는 방향에 참고한다.

관련 연구는 요구사항 생성·분류·품질 검사에 집중되어 있고, 실제 조달문서의 Draft-to-Final 변화 해석은 충분히 다뤄지지 않았다([LLM for RE SLR](https://arxiv.org/abs/2509.11446), [Generative AI for RE SLR](https://arxiv.org/abs/2409.06741)).

## 3. 시스템 설계

### 3.1 전체 구조

```text
HWP/PDF
→ pair 문서 JSON 변환
→ 변경 지점 추출
→ SFT 모델의 의미 해석
→ 최종 출력
```

문서 변환과 변경점 추출은 별도 전처리로 수행하고, SFT 모델은 제공된 변경 근거의 의미와 영향을 해석한다.

### 3.2 문서 표현과 분석 단위

HWP/PDF는 제목·표·목록과 페이지 정보가 유지된 JSON으로 변환한다. 요구사항은 문장 길이와 관계없이 하나의 의무를 나타내는 단위로 나누고, 각 단위에 원문 위치와 근거 ID를 붙인다.

### 3.3 Pairing·Alignment·Diff

먼저 공식 사업번호로 사전규격과 입찰공고가 같은 사업인지 확인한다.
이후 두 문서에서 서로 대응하는 요구사항을 찾아 다음과 같이 표시한다.

- 그대로 대응하거나 수정된 요구사항
- 여러 항목으로 분리되거나 하나로 합쳐진 요구사항
- 사전규격에서 삭제되거나 입찰공고에 새로 추가된 요구사항

각 결과에는 변경 전·후 원문, 직접 달라진 부분과 근거 ID를 저장한다.
단순 표현 수정과 실제 의무·범위·기한의 변화도 구분한다.

### 3.4 사용자 출력

**Case A: 단일 문서 분석**

1. 핵심 요구사항
2. 모호하거나 검증하기 어려운 요구사항
3. 구현 시 고려사항과 잠재 리스크
4. 발주기관에 추가로 확인할 사항

**Case B: 사전규격–입찰공고 비교 분석**

1. 변경 전·후 원문과 직접 달라진 부분
2. 변경이 일정·범위·비용·책임에 미치는 직접 영향
3. 변경에서 추론할 수 있는 발주기관의 우선순위와 신뢰 수준
4. 제안·구현 시 유의사항과 추가 확인사항

두 경우 모두 확인된 사실과 모델의 해석을 구분하고, 핵심 분석에는 원문 근거 ID를 함께 제시한다.

## 4. 학습 설계

### 4.1 원천데이터 수집

| 구분 | 원천 | 수집 내용 | 제공 방식 |
|---|---|---|---|
| 필수 | [나라장터 사전규격정보서비스](https://www.data.go.kr/data/15129437/openapi.do) | 사전규격번호, 사업명, 발주기관, 예산, 첨부파일 정보 | Open API·JSON |
| 필수 | [나라장터 계약과정통합공개서비스](https://www.data.go.kr/data/15129459/openapi.do) | 사전규격과 입찰공고를 연결하는 공고번호·발주계획번호·조달요청번호 | Open API·JSON |
| 필수 | 사전규격·입찰공고 첨부문서 | 요구사항 본문, 표, 목록과 제안·검증 조건 | HWP·HWPX·PDF |

### 4.2 학습데이터 정제

사업 Pair는 공식 식별자로 먼저 연결한다. 원본 파일, 변환본, 파싱 결과, 수집 시점과 출처 URL을 함께 보존하고, 초기에는 동일 사업 약 50건으로 파싱·Pairing·요구사항 단위가 적절한지 확인한 뒤 확대한다.

하나의 최종 학습 사례는 다음 두 부분으로 구성한다.

1. **입력**
   - 사업 정보와 사전규격·입찰공고의 대응 요구사항
   - 변경 전·후 원문, 근거 ID와 직접 달라진 부분
2. **Teacher가 완성한 정답 출력**
   - 확인된 변경 사실
   - 일정·범위·비용·책임에 미치는 직접 영향
   - 발주기관의 우선순위 또는 의도에 대한 해석
   - 해석을 뒷받침하는 근거, 신뢰 수준과 추가 확인사항

즉 전처리 결과와 Teacher 해석을 따로 저장하는 것이 아니라, **변경 근거에 Teacher의 해석을 붙인 하나의 구조화 분석 레코드**를 최종 Instruction Data로 사용한다. 다른 Teacher 또는 Verifier가 근거 불일치와 과대추론을 검사하고, 통과한 사례만 학습에 포함한다([Learning from Committee](https://aclanthology.org/2025.findings-acl.217/)).

학습·검증·평가 데이터는 같은 사업이나 유사 문서가 서로 섞이지 않도록 사업 단위로 분리한다.

### 4.3 학습 방법

본 프로젝트는 사전규격과 입찰공고의 **변경 근거에서 요구사항의 의미와 발주기관의 강조 변화를 해석하는 과정**을 학습한다. Student에게 전체 문서를 그대로 주기보다, 전처리 단계에서 연결한 변경 전·후 요구사항과 주변 문맥을 입력으로 제공한다.

학습 대상 출력에는 최종 결론만 넣지 않고 `변경 사실 → 직접 영향 → 해석 → 근거와 신뢰 수준`의 순서를 함께 넣는다. 이를 통해 Student가 Teacher의 문장 표현만 따라 하는 것이 아니라, 새로운 변경 사례에서도 같은 분석 순서를 적용할 수 있는지 확인한다.

## 5. 평가 설계

### 5.1 핵심 평가 지표

본 프로젝트의 핵심은 변화 유형 자체를 맞히는 것이 아니라, Teacher의 구조화 분석을 학습한 Student가 **새로운 문서에서도 근거에 맞는 해석을 생성하는지** 확인하는 것이다. Rationale Distillation 연구도 정답만 학습한 모델과 Rationale을 함께 학습한 모델의 과제 수행 성능을 비교한다([Distilling Step-by-Step](https://aclanthology.org/2023.findings-acl.507/), [Orca](https://www.microsoft.com/en-us/research/publication/orca-progressive-learning-from-complex-explanation-traces-of-gpt-4/)). 이를 본 과제에 맞게 다음 지표로 평가한다.

- **Distillation 개선도**
  - 구조화 분석 과정을 학습한 Student가 결과만 학습한 Student보다 높은 평가를 받은 비율을 확인한다.
- **Teacher 성능 유지도**
  - 동일 평가 Pair에서 Student의 해석 품질이 Teacher 평가점수의 어느 수준까지 도달했는지 확인한다.
- **근거 충실도**
  - 변경 사실과 해석이 제시된 원문 근거로 뒷받침되는지, 문서에 없는 이유를 추가하지 않았는지 평가한다. Claim을 근거 단위로 확인하는 방식은 [FActScore](https://aclanthology.org/2023.emnlp-main.741/)와 [AlignScore](https://aclanthology.org/2023.acl-long.634/)를 참고한다.
- **새 문서 일반화**
  - 학습에 없던 사업과 발주기관에서도 분석 순서와 해석 품질이 유지되는지 확인한다.

### 5.2 평가 방법

발주기관의 실제 변경 이유에는 하나의 정답이 없으므로, 문장 일치율이나 `의도 정확도` 대신 **LLM-as-a-Judge**를 중심으로 평가한다. Judge에는 변경 전·후 원문, Teacher 출력과 Student 출력을 함께 제공하고 다음 기준을 적용한다([G-Eval](https://arxiv.org/abs/2303.16634), [Prometheus 2](https://arxiv.org/abs/2405.01535)).

- **근거 정확성:** 인용한 변경 내용이 원문과 일치하는가?
- **해석 타당성:** 직접 영향과 우선순위 해석이 변경 근거에서 합리적으로 이어지는가?
- **과대추론 통제:** 문서에 없는 변경 사유를 확정적으로 만들지 않는가?
- **분석 유용성:** 제안·구현 관점에서 의미 있는 유의사항과 확인 질문을 제시하는가?

동일 평가세트에서 `프롬프트 모델`, `결과만 학습한 SFT`, `구조화 분석 SFT`, `Teacher`를 비교한다. 절대점수와 함께 두 응답 중 더 나은 것을 고르는 Pairwise 평가를 실시하며, 모델명은 숨기고 후보 순서를 바꿔 위치 편향을 줄인다([Judging the Judges](https://arxiv.org/abs/2406.07791)).

구조화 분석 SFT가 결과만 학습한 SFT보다 일관되게 우수하고 Teacher와의 격차를 줄였을 때 Distillation 효과가 있다고 판단한다.

## 7. 왜 이 문제를 SFT로 풀어야 하는가

이 프로젝트의 핵심 질문은 Teacher가 작성한 `변경 근거 → 변화 유형 → 직접 영향 → 해석 가설`의 분석 과정을 작은 모델이 학습할 수 있는가이다. 여기서 SFT의 역할은 Teacher의 숨겨진 사고를 그대로 복제하는 것이 아니라, **확인된 근거에서 출발해 사실과 해석을 구분하고 불확실성을 표시하는 외부 분석 절차**를 반복 학습시키는 것이다.

| 방법 | 강점 | 본 프로젝트에서의 한계·역할 |
|---|---|---|
| 프롬프트 엔지니어링 | 분석 기준과 JSON 출력 형식을 빠르게 시험하고 변경 가능 | 같은 문서에서도 변경 누락·레이블·근거 인용이 일정하지 않아 기준선으로 사용 |
| Preference 학습 | 여러 해석 중 근거가 충실하고 과대추론이 적은 응답을 선호하도록 최적화 가능 | 먼저 올바른 분석 과정과 비교할 후보 응답이 필요하므로 초기 단계의 우선 방법은 아님 |
| SFT | 변경 근거와 정답 분석 과정의 대응을 직접 학습해 절차와 형식을 내재화 | 변화 유형·직접 영향·근거 인용·불확실성 표현을 학습하는 본 프로젝트의 핵심 방법 |

문서 정렬과 Diff는 위 학습 방법과 경쟁하는 대안이 아니라 모델에 정확한 변경 후보를 제공하는 전처리다. 먼저 SFT로 구조화된 분석 행동을 학습한 뒤, 해석 품질을 더 세밀하게 조정할 필요가 확인되면 Preference 학습을 후속 적용한다.

### 7.1 프롬프트 사전 테스트

프롬프트만으로 두 문서의 변경 탐지와 의미 해석을 안정적으로 수행할 수 있는지 확인하기 위해 실제 사전규격·입찰공고 Pair를 Solar Open 2 250B에 10회 입력했다.

- **모델:** Solar Open 2 250B (`temperature 0.2`)
- **데이터:** 동일 과제에 대한 사전규격과 입찰공고 (변경지점 3개 이상 확인된 pair)
- **프롬프트:**

```text
당신은 공공조달 RFP 변경사항을 분석하는 전문가입니다.

아래의 사전규격 문서와 입찰공고 문서는 동일한 과제의 서로 다른 버전입니다. 제공된 두 문서만 근거로 비교하세요. 외부 지식, 관행, 추측을 사실처럼 추가하지 마세요.

분석 원칙:
1. 문서의 전체 내용을 요약하는 대신 실제로 달라진 요구사항을 찾으세요.
2. 표의 행·열이 PDF 파싱 과정에서 여러 블록으로 분리될 수 있으므로 인접 블록의 문맥을 함께 읽으세요.
3. 페이지 번호, 단독 기호, 서식 깨짐, 줄바꿈 차이, 반복 머리말처럼 사업적 의미가 없는 차이는 결과에서 제외하세요.
4. 동일한 내용의 단순 이동·재배치는 의미 변경으로 과대해석하지 마세요.
5. 각 변경에는 사전규격과 입찰공고의 근거 블록 ID를 모두 제시하세요. 한쪽에만 존재하는 변경은 해당 쪽 ID만 제시할 수 있습니다.
6. 변경 전·후 원문은 근거 블록의 표현을 그대로 사용하고, 여러 블록이면 읽을 수 있게 이어 붙이세요.
7. 발주자의 의도는 변경 내용으로 직접 뒷받침되는 범위에서만 추론하고 `supported`, `plausible_but_uncertain`, `unsupported`로 구분하세요.
8. 의미 있는 변경이 적으면 개수를 부풀리지 말고 발견한 것만 출력하세요.

대응 관계:
- `1:1`: 동일 요구사항의 수정
- `1:N`: 하나의 요구사항이 여러 요구사항으로 분할
- `N:1`: 여러 요구사항이 하나로 병합
- `1:0`: 사전규격 요구사항 삭제
- `0:1`: 입찰공고 요구사항 추가

변화 유형:
- `lexical`: 문구·단어·수치의 추가 또는 삭제
- `structural`: 장·절·표 이동, 요구사항 분할 또는 병합
- `semantic`: 의무 수준, 범위, 주체, 조건, 기한, 수치 또는 검증기준 변화

의미 변화 레이블:
- `scope_expanded`
- `scope_reduced`
- `obligation_strengthened`
- `obligation_weakened`
- `threshold_increased`
- `threshold_decreased`
- `responsibility_shifted`
- `deadline_changed`
- `deliverable_added`
- `verification_added`
- `technology_prescribed`
- `ambiguity_resolved`
- `wording_only`

출력은 설명이나 Markdown 코드 펜스 없이 다음 구조의 유효한 JSON 객체 하나로 작성하세요.

{
  "case_id": "입력의 case_id",
  "project_summary": "두 문서에 공통된 과제의 핵심을 2문장 이내로 요약",
  "changes": [{
    "change_id": "C01",
    "mapping": "1:1 | 1:N | N:1 | 1:0 | 0:1",
    "diff_types": ["lexical | structural | semantic"],
    "semantic_labels": ["허용된 의미 변화 레이블"],
    "prior_block_ids": ["prior_spec-B0001"],
    "bid_block_ids": ["bid_notice-B0001"],
    "before": "변경 전 원문",
    "after": "변경 후 원문",
    "changed_span": {"before": "직접 달라진 부분", "after": "직접 달라진 부분"},
    "direct_impact": "일정·범위·비용·책임·제안 준비 등에 미치는 직접 영향",
    "confidence": "high | medium | low"
  }],
  "issuer_intent": [{
    "claim": "변경에서 추론할 수 있는 발주자의 우선순위 또는 의도",
    "basis_change_ids": ["C01"],
    "support_level": "supported | plausible_but_uncertain | unsupported",
    "reason": "근거와 추론의 연결 설명"
  }],
  "uncertainties": [{
    "question": "문서만으로 확인할 수 없는 사항",
    "why_it_matters": "해석에 미치는 영향"
  }]
}

[사전규격 JSON]
{{PRIOR_SPEC_JSON}}

[입찰공고 JSON]
{{BID_NOTICE_JSON}}
```

| 항목 | 결과 |
|---|---:|
| 유효한 JSON 출력 | 10/10 |
| AI 교육 일정 변경 포착 | 10/10 |
| 입찰·서류 제출 마감 변경 포착 | 2/10 |
| 검증된 변경 전체 포착 | 0/10 |

모델은 JSON 형식과 일부 변경 분석은 수행했지만, 10회 모두 핵심 변경 전체를 찾지는 못했다. 또한 서로 다른 마감 변경을 하나로 합치거나, 일정 변경을 `wording_only`로 오분류하고, 존재하지 않는 근거 ID와 문서에 없는 발주 의도를 생성하는 오류가 나타났다.

이 결과는 오류를 두 범주로 나눠야 함을 보여준다. 긴 문맥에서 변경 후보를 놓치거나 표 구조를 잘못 연결하는 문제는 Alignment와 Diff로 보완해야 한다. 반면 **변경 단위 분리, 의미 레이블 선택, 근거 ID 복사, 사실·추론 분리와 불확실성 표현**은 일관된 정답 예시를 반복 제공하는 SFT에 적합하다.

따라서 `전체 원문 Prompt` → `정렬 원문` → `정렬 원문+Diff 후보` → `동일 입력+SFT 모델`을 순서대로 비교해 전처리와 SFT의 기여를 분리한다. SFT 이후에도 변경 Recall과 근거 정확성, 과잉추론 비율이 개선되지 않으면 데이터 확대보다 입력 구조와 학습 목표를 먼저 재검토한다.

## 8. 예상 난관과 대응 방안

1. **학습에 사용할 원천 사례 부족**
   - **발생 이유:** 사전규격과 입찰공고가 연결된 사업은 많지만 IT 분야로 제한하면 대상이 크게 줄어든다. 두 문서의 차이가 한 글자나 서식 수정에 그쳐 의미 있는 해석 사례로 쓰기 어려운 경우도 많다. 현재 확인 속도는 약 3개월에 적합한 사업 1건 수준이다.
   - **대응 방안:** 수집 기간을 확대하고 인접 ICT 분야까지 포함할 수 있는지 검토한다. 학습 단위도 사업 1건이 아니라 사업 안의 개별 변경 요구사항으로 나눠, 하나의 Pair에서 여러 Instruction 사례를 만든다.

2. **Teacher의 분석 과정이 Student의 추론에 실제로 영향을 미치는지 불확실**
   - **발생 이유:** Rationale을 함께 학습하면 작은 모델의 과제 성능이 향상된 선행 결과는 존재한다([Distilling Step-by-Step](https://aclanthology.org/2023.findings-acl.507/), [Orca](https://www.microsoft.com/en-us/research/publication/orca-progressive-learning-from-complex-explanation-traces-of-gpt-4/)). 다만 RFP 변경 해석처럼 정답이 하나가 아닌 과제에서 같은 효과가 나는지는 검증되지 않았다.
   - **대응 방안:** 결과만 학습한 모델과 구조화 분석 과정을 함께 학습한 모델을 동일 조건에서 비교한다. LLM Judge 평가에서 해석 타당성·근거 충실도·과대추론 통제가 일관되게 개선되는지를 Distillation 성공 기준으로 삼는다.

3. **Teacher의 Hallucination이 학습데이터에 포함될 위험**
   - **발생 이유:** 발주기관의 변경 이유는 문서에 직접 쓰여 있지 않은 경우가 많아, Teacher가 그럴듯하지만 근거 없는 의도를 만들어낼 수 있다. 잘못된 해석이 정답 데이터에 들어가면 Student도 같은 오류를 학습한다.
   - **대응 방안:** 모든 해석에 근거 변경 ID와 신뢰 수준을 붙이고, 문서에서 직접 확인되지 않는 내용은 가설로만 표현한다. 다른 Teacher 또는 Judge가 근거와 해석의 연결을 검토하고, 근거 없는 Claim이 포함된 사례는 학습에서 제외한다.
