이 문서는 이 프로젝트 안에서 특별한 뜻으로 쓰는 말만 설명한다. 일반적인 LLM 학습
용어는 다루지 않는다. 문서를 읽다가 아래 용어가 나오면 사전처럼 찾아보면 된다.

### 원천데이터

기관이 실제로 발행한 문서 원문이다. 모델이 만들거나 사람이 고친 데이터는 원천데이터가 아니다.

예) 인사혁신처가 홈페이지에 공개한 개인정보처리방침 원문은 `원천데이터`이다

원천데이터를 고르는 기준은 원천데이터 선정 프로세스.md에 있다.

### 데이터 유형

문서의 쓰임과 형식을 기준으로 나눈 큰 분류다.

예) `데이터 유형`은 개인정보처리방침, 표준약관, 제안요청서, 지원사업 공고·정정공고 등이 있다.

### 데이터 이름

실제로 수집한 원천데이터 묶음의 이름이다. 데이터 유형보다 구체적이다.

예) '인사혁신처 개인정보처리방침'은 개인정보처리방침 유형에 속하는 `데이터 이름`이다.

### 버전

버전은 같은 문서가 특정 시점에 공개된 한 가지 모습이다. 개정 전 문서와 개정 후 문서는 서로 다른 판본이다.

예) 'privacyOld1'부터 'privacyOld16'까지는 인사혁신처 개인정보처리방침의 `버전` 16개다.

### 문서 계열

하나의 기반 문서에서 이어진 모든 판본의 묶음이다.

예) 'privacyOld1'부터 'privacyOld16'까지 16개 판본은 인사혁신처 개인정보처리방침이라는 `문서 계열` 하나에 속한다.

학습용과 평가용 데이터를 나눌 때는 pair가 아니라 문서 계열을 기준으로 나눈다.
같은 문서 계열의 판본이 양쪽에 섞이면 학습에서 본 문서를 평가에서 다시 보게 되기 때문이다.

### 문서 단위 pair

비교 대상으로 확정한 문서 전체 두 편의 쌍이다.

예) '2022년 팁스 총괄 운영지침'과 '2023년 팁스 총괄 운영지침 일부개정'은 `문서 단위 pair` 중 하나다.

문서 제목이 비슷하다고 pair가 되지는 않는다. 양쪽 원문, 두 문서의 연결 근거, 실제 변경 내용을 모두 확인해야 한다.
문서 단위 pair를 선정하는 기준은 원천데이터 선정 프로세스.md의 `Pair acceptance rule`에 있다.

※ 버전 vs 문서 계열 vs 문서 단위 pair
- 판본은 문서A의 다양한 버전을 하나하나 가리킬 때 쓰는 말 (그것은 문서의 첫 번째 `버전`이다)
- 문서 계열은 문서A의 다양한 버전을 하나로 묶어 가리킬 때 쓰는 말 (그 문서들은 다 같은 `문서 계열`에 속한다)
- 문서 단위 pair는 문서A(개정전)와 문서A(개정후)의 쌍을 가리킬 때 쓰는 말 (그 문서에 대한 두 버전은 `문서 단위 pair`가 될 수 있다)

### 수정 단위 pair

문서 단위 pair 안에서 서로 비교하는 수정 전후 블록의 쌍이다. `블록쌍`이라고도 쓴다.

예) 아래 두 줄은 입찰 마감 시각이 바뀐 `수정 단위 pair` 중 하나다.

```text
[수정 전] 2026. 07. 02.(목) 11:00까지
[수정 후] 2026. 07. 10.(금) 14:00까지
```

보통 문서 단위 pair 한 건 안에는 십 수 개에서 수백 개의 수정 단위 pair가 나온다.

### 연결 근거

두 문서가 같은 문서 계열이거나 직접 이어진 문서임을 확인하는 단서다.

예) 같은 약관번호, 수정공고 본문에 적힌 원공고 번호, 지침 부칙의 시행일, 기관 홈페이지의 이전판 링크는 `연결 근거`로 사용 가능하다.

### 수집 기록

수집 기록은 문서 단위 pair를 어디서 언제 어떻게 받았는지 적어 둔 기록이다. 보통 manifest.json을 가리킬 때 쓴다.

예) `수집 기록`에는 원문 주소, 수집 시각, 파일 종류와 크기, SHA-256, 추출한 텍스트가 들어 있다.

### 배포용 문서

파일은 내려받을 수 있지만, 본문이 보호되어 텍스트를 꺼낼 수 없는 문서다.

예) 일부 팁스 총괄 운영지침 HWP 버전은 본문 추출이 되지 않은 `배포용 문서`이기에, 원천데이터 후보에서 제외했다.

### 변환본

다운로드 받은 HWP 원본을 텍스트 추출이 쉬운 HWPX로 바꾼 파일이다.

예) 신유형 상품권 표준약관의 2020년 HWP 원본은 `변환본(HWPX)`에서 블록을 추출해 2024년 판본과 비교했다.

변환본을 쓰는 까닭은 원본 HWP에는 없는 태그가 붙어, 그 단위로 수정 단위 pair를 구성하기 좋기 때문이다.

### 블록

블록(block)은 문서에서 텍스트를 꺼내 비교하는 최소 단위다. 사람이 읽는 문단 하나와 비슷하지만, 실제 단위는 파일 형식에 따라 달라진다.

예) HWPX는 문단 하나, 표 안에서는 셀의 문단 하나를 `블록`으로 본다. HTML은 문단·목록·표 셀처럼 줄이 나뉘는 부분을, TXT는 한 줄을 `블록`으로 본다.

### 조항

문서가 스스로 나눈 단위다. 제3조, 제1항, 제2호처럼 문서에 번호가 적혀 있다.

예) 하나의 `조항`이 여러 `블록`으로 쪼개질 수 있다. 블록은 파일 형식이 나눈 단위이고,
조항은 문서가 나눈 단위라서 서로 어긋난다.

### 변경 구간

비교 도구(difflib)가 전후 문서에서 다르다고 찾아낸 연속된 범위다.

예) 새 조항이 들어오면서 뒤 조항 번호가 모두 밀리면, 새 조항과 번호 변경이 하나의 `변경 구간`에 함께 잡힐 수 있다.

변경 구간 하나를 바로 수정 단위 pair 1건으로 세지 않는다. 구간 안을 블록으로 나누어 다시 판정한다.

### 변경 위치

수정 단위 pair 안에서 실제로 달라진 글자 범위다.

예) '2026. 07. 02. 11:00'이 '2026. 07. 10. 14:00'으로 바뀌었다면, 두 날짜·시각 문자열 자체가 `변경 위치`다. 문서 안의 좌표나 줄 번호를 뜻하지는 않는다.

### 대응 관계

수정 전 블록과 수정 후 블록이 서로 어떻게 이어지는지를 나타내는 값이다.

| 값 | 뜻 | 예 |
| --- | --- | --- |
| `1:1` | 블록 하나가 블록 하나로 바뀜 | 마감 시각 한 줄 변경 |
| `1:N` | 블록 하나가 여러 블록으로 나뉨 | 쿠키 설명 한 항이 세 항으로 나뉨 |
| `N:1` | 여러 블록이 하나로 합쳐짐 | 여러 조항이 하나의 조항으로 통합됨 |
| `0:1` | 새 블록이 생김 | 새 조항 신설 |
| `1:0` | 기존 블록이 사라짐 | 기존 조항 삭제 |

현재 문서에 대한 전처리는 `1:1`을 중심으로 작동한다. `1:N`과 `N:1`을 정확히 연결하는 일은 후순위로 넘겨두었다.

### 셈 규칙

무엇을 수정 단위 pair 1건으로 셀지 정한 규칙이다. 학습데이터 생성 프로세스.md 2-4절에서 자세한 내용이 존재한다.

예) 시스템 이름이 AP에서 AK로 문서 10곳에서 똑같이 바뀌었다면 이 수정사항은 `셈 규칙`에 따라 10건이 아니라 1건으로 센다.

### 문서 유사도

두 문서가 얼마나 겹치는지를 0과 1 사이 값으로 나타낸 것이다. 문서 단위 pair로 쓸 수 있는지 판단할 때 본다.

양쪽의 블록 목록을 통째로 비교해서, 양쪽에 그대로 있는 블록이 전체에서 차지하는 비율로 계산한다('difflib.SequenceMatcher'의 'ratio'). **세는 알갱이가 블록이다.**

예) 팁스 원공고와 수정공고는 `문서 유사도` 0.987이다. 거의 같고 다섯 군데만 바뀌었다는 뜻이다. 행안부 평가편람 2021 ↔ 2024는 0.016이라 같은 문서로 볼 수 없어 반려했다.

### 블록 유사도

블록 두 개가 얼마나 닮았는지를 0과 1 사이 값으로 나타낸 것이다. 수정 전 블록과 수정 후 블록을 짝지어 수정 단위 pair를 만들 때 본다.

계산 방법은 문서 유사도와 같지만 **세는 알갱이가 글자다.** 지금은 0.55를 넘는 짝만 이어 붙이고, 넘지 못하면 짝이 없는 것으로 보아 추가나 삭제로 처리한다.

예) '(2014. 09. 19. 개정)'과 '(2024. 2. 23. 개정)'은 `블록 유사도` 0.743이라 한 쌍으로 이어진다.

문서 유사도와 블록 유사도 기준값에는 아직 근거가 없다. 학습데이터 생성 프로세스.md 2-6절에 남겨둔 문제다.

### positive와 negative

실질 변경(문서의 의미가 달라지는 변경)이 있으면 positive, 글자 차이는 있지만 문서의 의미를 바꾸는 실질 변경이 없으면 negative다.

다른 문서에서 `실질 변경`이라고 쓴 것은 `positive`와 같은 말이다. 문장 안에서 풀어 쓸 때는 실질 변경, 라벨 값으로 적을 때는 positive를 쓴다.

예) '수집·이용'이 '수집ㆍ이용'으로 특수문자만 바뀐 것은 `negative`다. 쿠키를 사용하지 않던 기관이 쿠키를 사용한다고 바꾼 것은 `positive`다.

왜 생기는가? 파이썬의 difflib은 의미를 판단하지 않고 글자가 다른 부분을 모두 찾는다.
그렇다고 negative는 버리는 자료가 아니다. 모델이 사소한 편집을 중요한 개정으로 과장하지 않도록 가르치는 데 쓴다.

### 문서 단위 판정과 수정 단위 판정

positive와 negative는 문서 전체와 수정 단위 pair에서 각각 따로 판단한다.

| 판정 | 뜻 |
| --- | --- |
| 문서 단위 positive | 문서 안에 모델이 판단할 수정이 하나라도 있음 |
| 문서 단위 negative | 문서 안의 모든 차이가 기계 negative임 |
| 수정 단위 positive | 수정 단위 pair 하나에 실질 변경이 있음 |
| 수정 단위 negative | 수정 단위 pair 하나에 실질 변경이 없음 |

예) 새 조항이 하나 생기면 그 조항은 `수정 단위 positive`다. 그 뒤에서 조항 번호만 밀린 블록들은 `수정 단위 negative`지만, 새 조항이 남아 있으므로 문서 전체는 `문서 단위 positive`다. 문서 안의 모든 차이가 번호 밀림뿐일 때만 `문서 단위 negative`다.

### 기계 negative와 정규화 규칙

사람이나 모델이 읽지 않아도, 정해진 규칙(rule-base)만으로 negative라고 확정할 수 있는 것을 `기계 negative`라고 부른다.

`기계 negative`를 정의하는 것을 `정규화 규칙`으로 부르며, 현재 조항번호, 항목기호, 조항참조, 붙임번호, 목차 페이지, 따옴표, 가운뎃점, 띄어쓰기를 처리한다.

`기계 negative`는 모델의 해석 대상이 아니므로, 모델까지 도달하지 않는다.

### diff 훼손 금지 원칙

정규화 규칙은 자신이 맡은 차이만 지우고, 다른 차이는 남겨야 한다는 원칙이다.

예) 문서 맨 앞의 '제18조'가 '제19조'로 바뀐 것은 단순 번호 밀림(negative)일 수 있다. 하지만 문장 안의 '개인정보보호법 제25조'가 '제26조'로 바뀌었다면 근거 법조문이 달라진 실질 변경(positive)일 수 있다. 숫자만 보고 기계 negative로 분류하면 위험하다.

### 3단 라벨

모델이 수정 단위 pair의 변경 사항에 대해 한 번에 분류하지 않고 세 번에 나누어 기록하는 방식이다.

1. 실질 변경인가: positive / negative
2. 무엇이 바뀌었나: 대상 7종
3. 어떻게 바뀌었나: 방향 5종

#### 대상 7종

`무엇이 바뀌었는가`를 나타내는 일곱 가지 분류다.

- **기한·시점**: `신속하게 처리` → `10일 이내 처리`
- **수치·기준**: `제3조, 제3조의2, 제4조` → `제3조`
- **적용 범위**: `영상정보처리기기` → `고정형 영상정보처리기기`
- **수행 주체**: `발행자 등` → `발행자`
- **절차·요건**: `신속하게 조치` → `신분 확인 후 조치`
- **제출물·기재사항**: 위탁 현황 표에서 점검 결과 열 삭제
- **명칭**: `관리수준 진단` → `보호수준 평가`

#### 방향 5종

`어떻게 바뀌었는가`를 나타내는 다섯 가지 분류다.

- 늘었다 : 기간/금액/인원 등 수치 표현이 상승했다.
- 줄었다 : 기간/금액/인원 등 수치 표현이 감소했다.
- 다른 값 : A로 작성되던 내용이 B로 변화했다.
- 새로 생겼다 : 이전 문서에 없던 조항·조건·항목이 추가됐다.
- 없어졌다 : 이전 문서에 있던 조항·조건·항목이 삭제됐다.

> 참고: 대상 7종과 방향 5종은 현재 원천데이터를 분석해 만든 분류라, 데이터가 늘어나면 바뀔 수 있다. 두 목록을 곱한 35개 조합이 모두 가능한 것도 아니다. 예를 들어 명칭은 보통 '늘었다'나 '줄었다'와 함께 등장하지 않는다.

### 연산자

연산자(operator)는 대상 7종과 방향 5종 유형을 합쳐서 합성데이터 생성 쪽에서 부르는 이름이다.

예) (기한·시점, 늘었다)는 '이 조항의 처리 기한을 더 길게 바꿔라'라는 생성 지시를 `연산자`로 표현한 것이다.

### 기계 대조

사람의 해석 없이 두 값을 그대로 비교하는 검사다.

예) 생성할 때 "기한·시점이 늘었다"를 지시했고, 다시 판정한 결과도 "기한·시점이 늘었다"라면 `기계 대조` 결과 일치다.

### 왕복 검증

왕복 검증(round-trip)은 생성한 결과를 반대 방향으로 다시 판정해, 처음 지시와 같은 결과가 나오는지 보는 검사다.

예) '수치를 늘려라' → 수정된 문서 생성 → 지시를 감추고 다시 판정 → '수치가 늘었다'가 나오면 통과다.

### 분포 검사

데이터 한 건이 아니라 전체 묶음이 한쪽으로 치우치지 않았는지 보는 검사다.

예) 100건 중 99건이 같은 변경 유형(기한시점, 늘었다)이면, 각 데이터가 맞더라도 학습 자료로는 균형이 나쁘다.
