# Solar 생성기 적합성 blind 실험

이 실험은 Solar를 **학습데이터 생성자**로 쓸 수 있는지를 본다. Solar가 변경 탐지를
얼마나 잘하는지는 `../prompt_test/experiment_report.md`에서 이미 측정했고, 여기서는
그 다음 질문을 다룬다. 이미 정렬된 전후 블록쌍을 줬을 때, Solar가 SFT 레코드의 어느
칸을 채울 수 있는가.

blind는 눈가림을 뜻한다. 변경 유형 라벨을 알려주지 않고 전후 원문만 준 뒤, Solar가
텍스트만 보고 라벨을 복원하는지 본다. 사람이 만든 정답키와 대조해 일치율을 측정한다.

> **읽을 때 유의.** 이 보고서는 2026-08-04에 쓰였고 당시의 수치를 그대로 둔다. 이후
> 바뀐 것이 둘이다. 합성 목표 건수는 8,000건에서 **6,000건**이 됐고
> (`docs/기획서_최종.md`), 라벨 13종은 폐기되고 실제 20쌍에서 다시 귀납한 **3단
> 라벨**로 대체됐다(`docs/학습데이터_생성_프로세스.md` 2절). 결론은 그대로 유효하다 —
> 이 실험이 요구한 "정의서" 자체가 그 3단 라벨이기 때문이다.

## 결론

Solar는 `direct_impact` 작성에는 쓸 수 있고, 라벨 판정에는 쓸 수 없다.

의미 변화 라벨 일치율이 6건 중 3건이었고, 6건 모두 `confidence`를 `high`로 답했다.
틀린 답에도 `high`가 붙었으므로 이 필드는 신뢰도 신호가 아니다.

한편 불일치 3건 중 2건은 Solar의 답도 근거상 성립했다. 즉 **라벨 정의가 없어서 사람
정답키 자체가 흔들린 것**이며, 이것이 이번 실험의 가장 중요한 발견이다. 정의를
확정하기 전에는 8,000건 규모의 정답키를 만들 수 없다.

> 잠정 판정: 생성 파이프라인에서 Solar의 역할을 자연어 서술 한 칸으로 좁히고,
> `mapping`·`diff_types`·`semantic_labels`는 정렬 단계의 기계 산출로 채운다.
> 착수 조건은 라벨 13종의 정의서다.

## 실험 구성

- 모델: `solar-open2-250b`
- temperature `0.2`, top_p `1.0`, max_tokens `2048`, reasoning_effort `low`
- 동시 요청 6개 (`ThreadPoolExecutor`)
- 입력: 인사혁신처 개인정보처리방침 `privacyOld14` → `privacyOld15`
- 대상: 위 pair에서 추출한 실제 변경 6건
- 모델에 제공한 것: 전후 블록 원문, 대응 관계 5종, 변화 유형 3종, 의미 라벨 13종
- 모델에 제공하지 않은 것: 정답 라벨, 정답 대응 관계, 변경 요약
- 실행 결과: `runs/result_20260804.json`

변경 6건은 서식 잡음이 아니라 의미가 실제로 달라진 사례로 골랐다.

| ID | 변경 내용 |
| --- | --- |
| C1 | 쿠키를 사용하지 않는다 → 사용한다 (3개 항으로 확대 서술) |
| C2 | 재위탁 시 인사혁신처 동의를 받는다는 조항 신설 |
| C3 | 자동화된 결정에 대한 거부권과 그 제한 신설 |
| C4 | 관리수준 `진단` → `평가`, 근거 `제11조` → `제11조의2` |
| C5 | 요구서 명칭 `동의 철회` → `동의 정지` |
| C6 | 처리 목적 조항이 1개 항에서 3개 항으로 분할 |

## 관찰된 사실

### 1. `direct_impact`는 쓸 만하다

문장 품질이 일관되게 좋았다. 영향 대상을 정보주체·담당부서·수탁자로 나눠 쓰고,
문서에서 확인되는 범위 안에서 서술했다. C2가 대표 사례다.

- 원문 변경: `③ 「개인정보 보호법」 제26조 제6항에 따라 수탁자가 당사의 개인정보
  처리업무를 재위탁하는 경우 인사혁신처의 동의를 받고 있습니다.` 신설
- Solar 답: `수탁자는 개인정보 처리업무 재위탁 시 반드시 인사혁신처의 사전 동의를
  받아야 하며, 이를 위반할 경우 법적·계약적 책임을 질 수 있다. 인사혁신처는
  재위탁에 대한 통제권을 확보하여 개인정보 처리 과정의 안전성과 책임성을 강화할 수
  있다.`

SFT 레코드에서 사람이 쓰기 가장 번거로운 칸이 이 칸이고, 여기가 자동화된다면 30쌍을
8,000건으로 불리는 작업의 실질적인 병목이 사라진다.

### 2. `confidence`는 신호가 아니다

6건 전부 `high`였다. 라벨을 틀린 3건도 `high`였다. 현재 형태로는 검수 우선순위를
정하는 데 쓸 수 없다.

같은 입력을 여러 번 돌려 답이 흔들리는 정도를 신뢰도로 대체하는 방식이 대안이다.
자기 보고 대신 실측이므로 검증 가능하다.

### 3. 과잉추론이 재현됐다

`../prompt_test/experiment_report.md`의 실패유형 6번이 그대로 나타났다. C4가 그 사례다.

원문에서 달라진 것은 제도 명칭(`진단` → `평가`)과 근거 조항(`제11조` →
`제11조의2` 및 시행령 `제13조의2`)뿐이다. 평가 기준이 강화됐다는 서술은 어느 쪽
원문에도 없다.

Solar는 이렇게 답했다.

> 더 세분화된 법적 근거와 **시행령에 따른 강화된 평가 기준을 충족해야** 한다

근거 없는 강화 판단이며, `confidence`는 `high`였다. 이 유형은 `direct_impact`를
Solar에 맡기더라도 기계 검사나 표본 검수로 걸러야 한다는 뜻이다.

### 4. 라벨 정의 부재가 정답키를 흔들었다

불일치 3건 중 2건은 Solar의 오류로 보기 어렵다.

**C3(자동화된 결정)**: 정답키는 `scope_expanded`로 잡았고 Solar는 `scope_reduced`로
답했다. 신설 조항은 자동화된 결정이라는 새로운 영역을 방침에 들여왔다는 점에서
범위 확대이고, 동시에 정보주체의 거부권이 인정되지 않는 경우를 규정했다는 점에서
권리 범위 축소다. 두 판단 모두 원문에서 도출된다.

**C1(쿠키)**: 정답키는 `1:N`, Solar는 `1:0`으로 답했다. 이전판의 `사용하지 않습니다`
조항이 사라졌다고 보면 `1:0`이고, 같은 자리를 확대 서술이 대체했다고 보면 `1:N`이다.

두 사례 모두 라벨과 대응 관계에 정의가 없어서 생긴 문제다. 지금 프롬프트는 라벨
이름 13개를 나열할 뿐 각 라벨이 무엇을 가리키는지, 한 변경에 복수 라벨을 붙일 수
있는지, 확대와 축소가 동시에 성립할 때 무엇을 우선하는지를 정하지 않았다.

정의가 없으면 사람이 만든 정답키도 작성자마다 달라지므로, 라벨 일치율이라는 지표
자체가 성립하지 않는다.

## 처리량 실측

블록 단위 호출은 문서 전체 호출보다 훨씬 싸다. 같은 서버, 같은 모델의 두 실험을
비교한 값이다.

| | prompt tokens | completion tokens | 산출 |
| --- | ---: | ---: | ---: |
| 문서 전체 1회 (`prompt_test`) | 47,781 | 1,585 | 변경 3~5건 |
| 블록쌍 6회 (이 실험) | 2,220 | 1,084 | 변경 6건 |

블록쌍 6건을 처리하는 데 든 입력 토큰이 문서 전체 1회의 5% 미만이다. 생성 파이프라인을
블록 단위로 두면 컨텍스트 비용이 실질적인 제약이 되지 않는다.

소요 시간은 출력 길이가 좌우한다. `prompt_test`에서 측정한 단일 스트림 디코딩 속도는
약 94 토큰/초였다. 레코드당 출력을 1,000 토큰으로 잡으면 8,000건은 순차 실행 시 약
24시간이고, 동시 실행으로 줄일 수 있다. 이번 실험은 동시 6개로 문제없이 처리됐다.

## 다음 단계

1. **라벨 13종 정의서를 쓴다.** 각 라벨의 판정 기준, 복수 라벨 허용 여부, 확대·축소가
   동시에 성립할 때의 우선순위를 정한다. 이것이 나머지 모든 작업의 선행 조건이다.
2. 정의서를 적용해 같은 6건의 정답키를 다시 만들고 blind 일치율을 재측정한다. 정의
   때문에 흔들린 부분과 모델 오류를 분리하기 위해서다.
3. `confidence` 자기 보고를 제거하고, 같은 입력 반복 실행의 답 분산으로 대체한다.
4. 표본을 인사혁신처 15쌍 전체로 넓혀 `direct_impact`의 과잉추론 비율을 센다. C4 유형이
   몇 퍼센트인지 알아야 검수 비용을 추정할 수 있다.
5. 데이터 유형이 5종으로 늘어난 뒤 같은 실험을 반복해, 개인정보처리방침에서만 성립하는
   결과인지 확인한다.

## 이 실험이 답하지 않은 것

- 변경 탐지 성능. 이 실험은 정렬이 끝난 블록쌍을 전제했다.
- 합성 변경 생성. Solar에게 개정문을 쓰게 하는 역할은 검증하지 않았다.
- 개인정보처리방침 외 데이터 유형에서의 재현성.
