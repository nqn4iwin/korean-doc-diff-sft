# 02 공문서 차이 분석·해석 Solar 실험 결과

현재 실험 표본은 사전규격–입찰공고 문서쌍이다. 결과는 특정 RFP 유형에 한정된
표본 검증으로 해석하며, 이후에는 다른 공식 공문서 pair에도 같은 평가 기준을 적용한다.

## 결론

Solar Open 2는 긴 사전규격·입찰공고 원문에서 일부 실제 변경을 찾아 유효한 JSON으로
정리할 수 있었다. 그러나 10회 모두 검증된 변경점 전체를 빠짐없이 찾지는 못했으므로,
현재 입력 방식만으로는 안정적인 변경 탐지기로 보기 어렵다.

SFT 후보로서의 가치는 있다. 특히 출력 스키마 준수, 레이블 선택, 근거 ID 복사, 사실과
추론의 분리 같은 반복적인 행동 오류는 SFT로 개선할 가능성이 높다. 반면 긴 문서에서
중요 변경 후보 자체를 누락한 문제는 SFT만으로 해결된다고 가정하면 안 된다. 이 문제는
문서 정렬, 후보 추출, 구간별 비교 같은 입력 파이프라인 개선과 함께 검증해야 한다.

따라서 현재 잠정 판정은 다음과 같다.

> 프롬프트-only로 과제 수행 가능성은 확인했지만 안정성은 부족하다. SFT 적합 오류와
> 검색·정렬 적합 오류를 분리한 후, 최소한의 기계적 후보 추출을 결합한 추가 실험이 필요하다.

## 실험 구성

- 모델: `solar-open2-250b`
- 실행 횟수: 10회
- 성공한 API 호출: 10회
- 실패한 API 호출: 0회
- temperature: `0.2`
- top_p: `1.0`
- max_tokens: `8192`
- 재시도: 없음
- 입력:
  - 사전규격 976블록
  - 입찰공고 978블록
  - 렌더링된 프롬프트 약 113,805자
- 모델 입력에서 제외한 자료: `diff_summary.json`
- 실행 결과: `runs/02_20260731T093512.437864Z/`

## 평가 기준

사람이 문서 원문에서 확인하여 `diff_summary.json`에 기록한 핵심 변경은 다음 세 범주다.

1. 입찰 마감: `2026. 07. 02. 11:00`에서 `2026. 07. 10. 14:00`으로 변경
2. 서류 제출 마감: `2026. 07. 02. 18:00`에서 `2026. 07. 10. 18:00`으로 변경
3. AI 교육 일정: 7월 초 일정 삭제·조정 및 8월 일정 추가 예정

## 정량 결과

| 항목 | 결과 |
|---|---:|
| 유효한 JSON 출력 | 10/10 |
| AI 교육 일정 변경 포착 | 10/10 |
| 입찰·서류 제출 마감 변경 내용 포착 | 2/10 |
| 검증된 변경 전체 포착 | 0/10 |
| 응답별 변경 항목 수 | 3~5개 |

마감 변경을 찾은 2개 응답도 두 마감 변경을 별도 변경으로 안정적으로 분리하지 않았고,
존재하지 않는 블록 ID인 `prior_spec-B00369`, `bid_notice-B00371` 등을 생성했다.

## 관찰된 실패 유형

### 1. 중요한 변경 누락

가장 큰 문제다. 교육 일정 변경은 10회 모두 찾았지만, 입찰 및 서류 제출 마감 변경은
대부분 놓쳤다. 같은 입력과 낮은 temperature에서도 재현율이 안정되지 않았다.

긴 입력에서 특정 위치의 차이를 발견하지 못한 문제이므로 SFT로 개선될 가능성은 있지만,
SFT만으로 완전 재현을 보장하기 어렵다. 비교 후보를 미리 좁히거나 문서를 구간별로 정렬해
주는 구조가 더 직접적인 해결책이다.

### 2. 변경 단위 분리 실패

입찰 마감과 서류 제출 마감은 서로 다른 필드이지만, 이를 하나의 변경 항목에 합치거나
`changed_span`에는 한쪽만 기록했다. 이 문제는 올바른 Requirement Atom 또는 필드 단위
정답을 학습시키면 SFT로 개선하기 좋은 유형이다.

### 3. 의미 레이블 오분류

실제 일정 변경을 주로 `ambiguity_resolved`로 분류했고, 일부 응답은 직접 영향이 있는 일정
변경을 `wording_only`로 분류했다. 현재 허용 레이블에는 일반 일정 변경을 정확히 나타내는
레이블이 `deadline_changed`밖에 없어 레이블 체계 자체도 보완할 필요가 있다.

레이블 정의를 먼저 명확히 한 뒤 일관된 정답 예시를 제공하면 SFT로 교정 가능한 문제다.

### 4. 근거 블록 ID 오류

대부분은 실제 블록 ID를 사용했지만, 마감 변경을 찾은 응답에서 존재하지 않는 ID를
생성했다. 출력 후 ID 존재 여부를 기계적으로 검사할 수 있고, SFT에서는 입력에 있는 ID만
복사하도록 학습시킬 수 있다. 생성 제약 또는 후처리와 함께 해결하기 적합하다.

### 5. 표 셀 대응 오류

PDF 표가 여러 블록으로 분리되면서 장소 셀과 `8월 일정 1회 추가 예정` 문구를 직접적인
전후 관계로 잘못 연결한 응답이 있었다. 이는 모델 행동 문제이기도 하지만 원천 파싱에서
행·열 구조가 사라진 영향이 크다. 표 구조를 보존하지 않은 채 SFT만 적용하면 다른 표에서도
같은 오류가 반복될 수 있다.

### 6. 발주 의도 과잉추론

문서에 없는 `여름 휴가 시즌`, `내부 사정`, `제안사의 유연성 평가`, `분쟁 최소화` 등을
`supported`로 판정한 사례가 있었다. 사실, 직접 영향, 가능한 의도를 분리한 정답과
`plausible_but_uncertain`·`unsupported` 반례를 학습시키면 SFT로 개선하기 좋은 문제다.

## SFT로 해결 가능한 범위

### SFT 적합도가 높은 문제

- 항상 유효한 목표 스키마으로 출력하기
- 서로 다른 변경 필드를 별도 Atom으로 분리하기
- 일정 변경을 `wording_only`로 분류하지 않기
- 입력에 존재하는 블록 ID만 인용하기
- 변경 전·후 원문과 `changed_span`을 일치시키기
- 직접 확인된 사실과 발주 의도 추론을 분리하기
- 문서에 없는 변경 사유의 신뢰 수준을 낮추기
- 불확실한 사항을 `uncertainties`로 보내기

### SFT만으로 해결을 장담하기 어려운 문제

- 약 11만 자 입력 전체에서 모든 중요한 변경을 빠짐없이 찾기
- 파싱 과정에서 소실된 표의 행·열 관계 복원하기
- 서로 멀리 떨어진 블록을 정확한 전후 요구사항으로 정렬하기
- 새로운 문서 형식과 새로운 표 구조에 일반화하기
- 천 건 단위 처리에서 누락률을 일관되게 유지하기

SFT가 모델의 비교 습관과 출력 행동을 개선할 수는 있지만, 모델이 보지 못했거나 잘못
정렬한 후보를 사후에 복구하는 수단은 아니다. 특히 현재 실험의 핵심 실패인 마감 변경
누락은 학습 데이터 부족뿐 아니라 긴 문맥에서의 탐색 문제일 가능성이 있다.

## 다음 실험 제안

SFT 데이터 제작 전에 아래 순서로 원인을 분리하는 것이 좋다.

1. 현재 프롬프트와 원문 입력을 유지한 채 평가기를 만들어 변경별 recall과 근거 ID 정확도를
   자동 집계한다.
2. 사전규격과 입찰공고를 장·절·표 또는 유사 블록 단위로 기계 정렬한 입력으로 같은 모델을
   다시 10회 실행한다.
3. 단순 문자열·수치 차이 후보만 함께 제공하는 조건을 추가하여 마감 변경 회수율을 비교한다.
4. 입력 개선만으로 누락이 줄어드는지 확인한 뒤에도 남는 레이블·근거·추론 오류를 SFT
   대상으로 선정한다.
5. SFT 학습 예시는 정답 변경뿐 아니라 `변경 없음`, `wording_only`, `근거 부족 추론` 반례를
   함께 포함한다.

비교할 최소 실험군은 다음과 같다.

| 실험군 | 입력 | 목적 |
|---|---|---|
| A | 현재 전체 원문 | 현재 baseline 재현 |
| B | 장·절·표 단위 정렬 원문 | 정렬 효과 측정 |
| C | 정렬 원문 + 기계적 diff 후보 | 후보 추출 효과 측정 |
| D | C 입력 + SFT 모델 | SFT의 순수 추가 효과 측정 |

이 순서를 지켜야 SFT가 필요한 것인지, parser·alignment 개선만으로 충분한 것인지, 또는 둘 다
필요한지를 구분할 수 있다.

## SFT 데이터 설계 시 주의점

- 현재 한 건을 10회 반복한 결과를 서로 다른 10개 학습 사례처럼 취급하지 않는다.
- 동일 과제의 다양한 문서 pair를 확보하여 문서 형식과 변경 유형의 다양성을 만든다.
- gold에는 변경 전·후 블록 ID, 원문 span, 대응 관계, 변화 유형, 직접 영향과 신뢰도를
  사람이 검증하여 기록한다.
- 발주 의도는 단일 정답 문장보다 `supported`, `plausible_but_uncertain`, `unsupported`의
  판정 근거를 학습 대상으로 삼는다.
- 학습·검증·시험 분할은 공고 건 단위가 아니라 동일 사업 계열 또는 발주기관의 유사 양식이
  서로 새지 않도록 구성한다.
- SFT 평가는 문장 유사도보다 변경별 precision/recall, 근거 ID 유효성, span 정확성,
  과잉추론 비율을 우선한다.

## 기획 세션에서 결정할 사항

1. 02의 목표를 `전체 변경 탐지`로 둘지, `기계적으로 추출된 변경 후보의 의미 해석`으로
   좁힐지 결정한다.
2. 일정 변경용 의미 레이블을 새로 추가할지 결정한다.
3. Requirement Atom 및 표 구조 정렬을 parser 책임으로 둘지 별도 alignment 단계로 둘지
   결정한다.
4. SFT 착수 조건이 될 최소 pair 수와 변경 Atom 수를 정한다.
5. baseline 대비 어떤 지표 개선을 SFT 성공 기준으로 볼지 정한다.
