# data_collect

4개의 AI 활용 아이디어에 대해 **데이터 수집 파이프라인을 구축하고, 실제로
SFT 데이터셋까지 생성할 수 있는지 검증하는 실험용 저장소**다.

이 저장소의 목적은 모델 학습, 서비스 UI 구현 또는 운영 시스템 개발이 아니다.
각 아이디어에 필요한 원천 데이터를 어디에서 얼마나 안정적으로 수집할 수 있는지,
수집한 자료를 학습 가능한 입력-정답 쌍으로 변환할 수 있는지, 그 과정에서 어느
정도의 자동화와 수작업 검수가 필요한지를 확인하는 데 집중한다.

검토 대상 아이디어의 상세한 정의는 [아이디어.md](아이디어.md)를 참고한다.

## 검증 대상

1. 공공/사업 문체로 문서 작성 모델
2. 공공데이터 활용 사전검토 챗봇
3. 공공사업 보고서·RFP 분석 모델
4. 회의기록 기반 사내 업무 이력 문의 챗봇

각 아이디어의 파이프라인은 다음 질문에 답해야 한다.

- 원천 데이터의 출처와 이용조건을 기록할 수 있는가?
- 데이터를 반복해서 수집하거나 내부 반입 자료를 일관되게 처리할 수 있는가?
- 문서 본문과 표, 페이지, 메타데이터를 필요한 수준으로 추출할 수 있는가?
- SFT에 사용할 입력-정답 쌍을 생성할 수 있는가?
- 실제 자료, 규칙 기반 라벨, 합성 자료를 구분할 수 있는가?
- 개인정보·기밀정보 제거와 품질 검사를 자동화할 수 있는가?
- 최종 샘플 수, 파싱 성공률, 합성 데이터 비율과 수작업 검수량은 어느 정도인가?

## 목표 저장소 구조

각 아이디어 디렉터리는 독립적으로 수집부터 데이터셋 생성과 검증까지 실행할 수
있게 구성한다. 실제 구현 과정에서 필요하지 않은 파일은 만들지 않고, 아래 구조를
기본 설계로 사용한다.

│   ├── provenance.py              # 출처·이용조건·수집시각 기록

있다.

## 공통 데이터 흐름

```text
원천 목록 작성
  → 수집 또는 내부 자료 반입
  → raw 파일과 출처 manifest 저장
  → 본문·표·메타데이터 파싱
  → 정규화 및 비식별화
  → 입력-정답 후보 생성
  → 규칙 검사 및 표본 수동 검수
  → SFT JSONL과 수집 가능성 보고서 생성
```

데이터 단계는 다음과 같이 구분한다.

- `raw`: 원본 그대로의 파일과 API 응답
- `interim`: 파싱·정규화·비식별화를 거친 중간 산출물
- `processed`: 스키마 검증을 통과한 SFT 또는 평가용 JSONL
- `manifests`: URL, 문서 ID, 수집시각, 체크섬, 이용조건, 처리상태
- `reports`: 수집 건수, 실패 사유, 파싱률, 유효 샘플 수, 합성 비율

## 데이터 등급

모든 학습 샘플에는 정답 생성 방식을 표시한다.

- `gold`: 사람이 작성하거나 직접 검증한 입력-정답 쌍
- `silver`: 사내 최종 결과물, 업무 대응표 또는 규칙 기반으로 연결된 쌍
- `synthetic`: 모델이나 템플릿으로 생성한 입력 또는 정답

합성 데이터는 실제 데이터와 섞어 출처를 잃지 않도록 하며, 가능성 평가 시 전체
샘플 수뿐 아니라 등급별 수량과 사람의 검수 필요량을 함께 보고한다.

## 공통 산출물

각 아이디어의 실험이 끝나면 최소한 다음 결과를 남긴다.

```text
manifests/<idea>.jsonl
data/<idea>/processed/train.jsonl
data/<idea>/processed/validation.jsonl
reports/<idea>.md
```

보고서에는 다음 내용을 포함한다.

- 접근 가능한 원천과 실제 수집 성공 건수
- 문서 형식별 파싱 성공률 및 실패 원인
- 생성한 SFT 샘플 수와 Gold/Silver/Synthetic 비율
- 중복·개인정보·출처·스키마 검사 결과
- 샘플 1건당 예상 수작업 검수량
- 해당 아이디어의 데이터셋 구축 가능/조건부 가능/어려움 판단

## 데이터 관리 원칙

- 원본 사내 문서와 대용량 공개자료는 Git에 커밋하지 않는다.
- API 키, 인증정보와 사내 경로는 환경변수 또는 로컬 설정으로 관리한다.
- 원본 대신 재수집 가능한 manifest와 익명화된 소량의 테스트 fixture를 관리한다.
- 공개자료도 데이터별 이용조건, 출처, 수집일을 함께 기록한다.
- 사내 데이터는 승인된 범위 안에서만 반입하고 개인정보와 불필요한 식별정보를
  학습 데이터 생성 전에 제거한다.
- 중복 제거와 train/validation/test 문서 단위 분리를 수행해 데이터 누수를 막는다.
