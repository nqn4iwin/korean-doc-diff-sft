# 02. 공공사업 RFP 분석 데이터

나라장터 등에 공개된 제안요청서·과업지시서·규격서에서 요구사항, 일정, 산출물,
평가항목과 위험조건을 구조화하는 SFT 데이터셋을 실제로 구축할 수 있는지 검증한다.

이 디렉터리의 목적은 PDF 파서, OCR 엔진, 입찰 분석 서비스 또는 모델 자체를
개발하는 것이 아니다. 문서 처리 모듈이 페이지와 표 구조를 보존하여 추출한 결과를
입력으로 사용하고, 다음과 같은 근거 기반 정답을 얼마나 만들 수 있는지 확인한다.

```text
RFP 원문 블록과 표
→ 명시된 요구사항·기한·산출물·배점 추출
→ 원문 위치와 정규화 값 연결
→ 모호하거나 위험한 조건의 별도 검토
→ 발주처 확인 질문 후보 생성
```

공개된 문서라는 이유만으로 학습·재배포가 허용된다고 가정하지 않는다. 원천별
이용조건을 기록하고, 원문 파일은 Git에 커밋하지 않으며, 외부 공개가 허용되지 않은
자료에서 만든 파생 데이터도 공개 산출물과 분리한다.

## 현재 상태

- 2026년 7월 28일 기준 공식 수집 후보로 조달청의 나라장터
  `입찰공고정보서비스`와 `사전규격정보서비스`를 확인했다.
- 입찰공고정보서비스는 업무별 공고 목록·상세정보·변경이력을 제공한다.
- 사전규격정보서비스는 사업명, 배정예산액, 관련 규격서 파일과 규격서 의견을
  제공한다고 명시되어 있어 문서 확보의 우선 원천으로 적합하다.
- 2026년 7월 28일에 두 서비스의 활용신청과 인증키 설정을 완료했다.
- 같은 날 서비스별 최근 24시간 용역 목록 1건 연결 검사를 완료했다.
  - 사전규격정보서비스: HTTP 200, 응답코드 `00`, 전체 212건
  - 입찰공고정보서비스: HTTP 200, 응답코드 `00`, 전체 684건
- 연결 진단 과정에서 서비스별 외부 요청을 최대 5회 사용했다. 실패 요청의 포털
  차감 여부는 확인하지 않았으므로 당일 예산에서는 모두 사용한 것으로 계산한다.
- 두 서비스의 개발계정 트래픽은 각각 일 1,000건이다. 최초 연동은 서비스별
  1건만 호출하고, 이후 수집기도 실행별 요청 예산과 페이지 상한을 필수로 둔다.
- API 응답에서 첨부파일 URL·파일명·공고 차수·정정 이력을 어느 수준까지 연결할 수
  있는지는 아직 검증하지 않았다.
- PDF·HWP·HWPX·DOCX의 실제 비율과 형식별 파싱 성공률도 아직 측정하지 않았다.
- 현재 잠정 판단은 **조건부 가능**이다. 공개 문서는 충분할 가능성이 높지만,
  신뢰할 수 있는 정답 라벨은 자동 추출만으로 확보하기 어렵다.

세부 작업 상태와 완료 조건은 `docs/PLAN.md`에서 관리한다.

## 검증 범위

### 1차 범위

- 나라장터의 용역 입찰공고와 사전규격
- 제안요청서, 과업지시서, 규격서와 제안서 평가기준
- 텍스트 레이어가 있는 PDF
- 문장·목록·표에서 명시적으로 확인되는 다음 항목
  - 요구사항과 의무 강도
  - 일정, 기한과 수행 주기
  - 제출 산출물
  - 평가항목과 배점
  - 투입인력과 자격 조건
  - 예산·수량·비율 등 수치 조건
- 원문 근거가 있는 모호성·위험조건과 발주처 확인 질문

### 후속 범위

- HWP·HWPX·DOCX 문서
- 이미지 기반 스캔 PDF와 OCR 결과
- 정정공고 전·후 문서의 변경점
- 사전규격 의견과 최종 RFP의 반영 여부
- 사용 승인을 받은 사내 요구사항 대응표와 과거 검토 자료

### 제외 범위

- 제안서 자동 작성과 낙찰 가능성 예측
- 법률적 책임 또는 계약 위험의 최종 판단
- 공고에 없는 발주기관 의도 추정
- 원문 근거 없이 관행만으로 생성한 요구사항
- CAPTCHA, 로그인 또는 접근통제를 우회하는 첨부파일 수집

## 데이터 원천

### 1. 나라장터 사전규격정보서비스

- 제공처: 조달청
- 공식 안내:
  [공공데이터포털 사전규격정보서비스](https://www.data.go.kr/data/15129437/openapi.do)
- API 기준 주소: `apis.data.go.kr/1230000/ao/HrcspSsstndrdInfoService`
- 인증방식: 공공데이터포털 일반 인증키와 서비스 활용신청
- 이 프로젝트에서의 역할: **문서 후보와 초기 메타데이터**

공식 설명상 물품·용역·외자·공사별 사전규격 목록, 사업명, 배정예산액, 관련
규격서 파일과 규격서 의견을 제공한다. 1차 실험에서는 `용역` 목록을 우선 사용한다.

검증할 항목:

- 사전규격등록번호와 사업명
- 수요기관, 공개일과 의견등록 마감일
- 배정예산액
- 관련 규격서 파일명과 다운로드 위치
- 규격서 의견의 존재 여부와 원문 연결 키
- 같은 사업의 중복 등록 또는 변경 이력

### 2. 나라장터 입찰공고정보서비스

- 제공처: 조달청
- 공식 안내:
  [공공데이터포털 입찰공고정보서비스](https://www.data.go.kr/data/15129394/openapi.do)
- API 기준 주소: `apis.data.go.kr/1230000/ad/BidPublicInfoService`
- 인증방식: 공공데이터포털 일반 인증키와 서비스 활용신청
- 이 프로젝트에서의 역할: **최종 공고 메타데이터와 변경 추적**

공식 설명상 물품·용역·공사·외자별 공고 목록, 상세정보, 기초금액, 제한정보와
공고 변경이력을 제공한다. 1차 실험에서는 용역 공고를 대상으로 다음 연결 가능성을
확인한다.

```text
사전규격등록번호
→ 입찰공고번호와 공고차수
→ 최종 제안요청서·과업지시서
→ 정정공고와 첨부파일 변경
```

공고 API가 모든 첨부문서를 직접 제공한다고 미리 가정하지 않는다. 실제 응답을
확인하여 공식 다운로드 URL이 포함된 경우에만 자동 수집하고, 그렇지 않으면
manifest에 공고 상세 페이지와 수동 반입 상태를 기록한다.

### 3. 사내 검토 자료

사용 승인을 받은 경우에만 다음 자료를 보조 원천으로 반입한다.

- 과거 RFP 검토표
- 요구사항 대응표
- 발주처 질의 목록과 답변
- 정정 전·후 비교표
- 제안서 작성 과정의 이슈 목록

이 자료는 공개 RFP에 사람의 실제 판단을 연결할 수 있어 가치가 높지만, 기밀정보,
개인정보와 제안사의 영업정보를 포함할 수 있다. 승인 범위와 외부 전송 가능 여부를
확정하기 전에는 반입·파싱·합성에 사용하지 않는다.

## 태스크 분리

### A. 원문 사실 추출

원문에 명시된 내용을 구조화한다.

- 요구사항 본문
- 요구사항 분류
- 필수·선택·조건부 여부
- 주체, 행위와 대상
- 일정, 기한과 반복 주기
- 산출물
- 수치, 단위와 배점
- 투입인력과 자격
- 원문 페이지, 절 경로와 표 셀 위치

이 태스크는 원문과 직접 대조할 수 있으며 Gold 또는 Silver 라벨을 만들 수 있다.

### B. 위험조건 검토

원문 조항이 만들 수 있는 불확실성을 구조화한다.

- 범위가 정의되지 않은 추가 업무
- 횟수·수량·완료조건이 없는 의무
- 발주기관 요청에만 의존하는 일정 또는 산출물
- 검수·승인 기준의 부재
- 상충하는 일정·인력·배점 조건
- 개인정보·보안·지식재산권·손해배상 관련 확인 필요사항

위험 판단은 원문에 그대로 적힌 사실이 아니다. 따라서 자동 생성 결과를 Gold로
간주하지 않고 다음 세 요소를 사람이 함께 검수한다.

```text
근거 조항
→ 위험으로 판단한 이유
→ 발주처에 확인할 구체적인 질문
```

## 문서와 라벨 단위

### 문서 식별

동일 사업의 파일과 정정본을 섞지 않도록 최소한 다음 키를 보존한다.

- `notice_id`: 입찰공고번호
- `notice_round`: 공고차수
- `prior_spec_id`: 사전규격등록번호
- `document_id`: 원천·공고·파일 체크섬으로 만든 내부 ID
- `document_type`: 제안요청서·과업지시서·규격서·평가기준·공고서
- `source_file_sha256`
- `published_at`와 `collected_at`
- `supersedes_document_id`: 이전 버전 연결

### 원문 위치

모든 라벨은 다음 위치정보 중 가능한 값을 가져야 한다.

- PDF 파일 기준 페이지 인덱스
- 문서에 인쇄된 페이지 번호
- 장·절·항목 경로
- 문단 또는 목록 항목 ID
- 표 ID, 행과 열
- 검수에 필요한 짧은 근거 텍스트

PDF 파일 페이지와 문서에 인쇄된 페이지가 다를 수 있으므로 하나의
`source_page` 값으로 합치지 않는다.

### 요구사항 정답 후보

```json
{
  "requirement_id": "REQ-0001",
  "category": "project_management",
  "modality": "mandatory",
  "subject": "사업자",
  "action": "제출",
  "object": "착수계획서",
  "condition": "사업 착수 후",
  "deadline_text": "10일 이내",
  "deadline_value": 10,
  "deadline_unit": "day",
  "deliverable": "착수계획서",
  "source": {
    "document_id": "DOC-...",
    "pdf_page_index": 24,
    "printed_page": 25,
    "section_path": ["제5장", "사업관리 요구사항"],
    "block_id": "p024-b007"
  },
  "label": {
    "grade": "gold",
    "method": "human_verified",
    "review_status": "approved"
  }
}
```

실제 스키마 파일은 문서 표본과 API 응답을 확인한 뒤 작성한다. 위 예시는 필요한
정보 경계를 정하기 위한 설계이며 확정 스키마가 아니다.

## 요구사항 분류 초안

- `business`: 사업 목적과 업무 범위
- `functional`: 구현해야 하는 기능
- `non_functional`: 성능·가용성·품질
- `data`: 데이터 수집·이관·품질·보존
- `interface`: 연계 시스템과 인터페이스
- `security_privacy`: 보안·개인정보
- `project_management`: 보고·회의·형상·변경관리
- `deliverable`: 제출물과 납품물
- `personnel`: 인력·경력·자격·상주 조건
- `schedule`: 착수·단계·완료 일정
- `evaluation`: 평가항목·배점·정량 기준
- `contract`: 검수·대가·지식재산권·책임
- `other`: 자동 분류가 불확실하여 검수가 필요한 항목

분류체계는 첫 표본에서 실제 문서의 장 구성과 요구사항 코드 체계를 조사한 후
합치거나 세분화한다.

## 데이터 처리 단계

```text
API 메타데이터 수집
→ 공고·사전규격·첨부파일 관계 manifest 작성
→ 허용된 첨부파일 다운로드 또는 수동 반입
→ 파일 형식·텍스트 레이어·암호화 여부 판별
→ 페이지·문단·목록·표를 보존한 문서 중간표현 생성
→ 규칙 기반 요구사항 후보 탐지
→ 사람의 원문 대조와 라벨 확정
→ 사실 추출 SFT와 위험 검토 SFT를 별도 생성
→ 문서 단위 데이터 분리와 검증
→ 수집 가능성 보고서 작성
```

- `raw`: API 응답과 원본 첨부파일
- `interim/documents`: 페이지·블록·표 구조를 보존한 문서 중간표현
- `interim/candidates`: 규칙 또는 모델이 찾은 미검수 후보
- `interim/labels`: 검수 상태를 포함한 구조화 라벨
- `processed`: 스키마와 근거 검증을 통과한 SFT·평가 JSONL

## 데이터 등급

- `gold`: 사람이 원문 위치와 구조화 값을 직접 대조한 라벨
- `silver`: 명시적인 요구사항 코드, 표 구조 또는 사내 대응표로 연결하고 표본
  검수를 통과한 라벨
- `synthetic`: 원문을 바탕으로 모델이나 템플릿이 생성한 질문·오답·위험 설명
- `human_review_required`: 근거는 있으나 의무 강도, 범위 또는 위험 해석이 불확실함
- `excluded`: 원문 위치를 복원할 수 없거나 권리·품질 기준을 만족하지 못함

`gold`는 문서가 공식 문서라는 뜻이 아니라 해당 구조화 정답을 사람이 검증했다는
뜻이다. 규칙이나 LLM이 추출한 후보는 검수 전까지 Gold로 승격하지 않는다.

## 인증정보와 호출 한도 설정

`config.example.env`를 참고하여 이 디렉터리에 로컬 `.env`를 만든다. 두 서비스의
인증키를 하나로 합치지 않고 각각 별도 변수에 설정한다.

```dotenv
G2B_PRIOR_SPEC_SERVICE_KEY=사전규격정보서비스 일반 인증키
G2B_BID_NOTICE_SERVICE_KEY=입찰공고정보서비스 일반 인증키
RFP_API_MAX_REQUESTS_PER_RUN=1
RFP_API_MAX_PAGES_PER_RUN=1
RFP_API_MAX_RETRIES=0
```

위 값은 최초 연동용이다. 서비스별로 목록 1건이 정상 응답하고 호출량 기록을
확인하기 전에는 상한을 높이지 않는다. `.env`와 인증값이 포함된 요청 URL은 Git,
manifest, 로그와 채팅에 남기지 않는다. 포털의 Encoding·Decoding 키는 테스트
코드가 내부에서 정규화하며 원본 키는 출력하지 않는다.

두 인증키를 출력하거나 응답 원문을 저장하지 않고 서비스별 목록 1건만 호출한다.

```powershell
python .\02_rfp_analysis\crawlers\test_connections.py
```

5. 위험조건 라벨의 표본 검수에 참여할 실무 검토자를 정한다.

## Codex 작업 원칙

이 디렉터리에서 새 Codex 세션을 시작하면 다음 순서로 작업한다.

1. 이 `README.md`와 `docs/PLAN.md`를 먼저 읽는다.
2. 저장소 루트의 `AGENTS.md`와 현재 Git 상태를 확인한다.
3. API 활용신청과 인증키 로컬 설정 여부만 확인하고 인증값 자체를 요구하지 않는다.
4. 실제 API 응답을 보기 전에 첨부파일 필드나 연결 키를 확정하지 않는다.
5. 문서 표본을 보기 전에 형식별 파서와 확정 스키마를 만들지 않는다.
6. 서비스별 일 1,000건 한도를 넘지 않도록 호출 전 실행 예산을 계산하고, 응답이
   비정상이면 무제한 재시도하지 않는다.
7. 원문 사실 추출과 위험 판단을 서로 다른 태스크와 데이터 등급으로 유지한다.
8. 모든 정답이 문서 ID와 원문 위치로 역추적되는지 검증한다.
9. 정정본은 이전 문서를 덮어쓰지 않고 별도 버전으로 보존한다.
10. train·validation·test는 블록이 아니라 공고 또는 사업 단위로 분리한다.
11. 결과를 문서 수, 파싱률, 유효 라벨 수와 수동 검수량으로 보고한다.

## 1차 판정 기준

- **구축 가능:** 공개 원천에서 문서를 반복 수집할 수 있고, 원문 위치를 보존한
  요구사항 라벨을 수용 가능한 검수량으로 확보할 수 있다.
- **조건부 가능:** 문서 수집과 사실 추출은 가능하지만 표·페이지 복원 또는 위험
  라벨 생성에 상당한 수작업과 사내 대응표가 필요하다.
- **어려움:** 첨부파일을 안정적으로 확보할 수 없거나, 대부분이 파싱 불가능하고,
  원문 근거가 있는 라벨을 만드는 비용이 지나치게 크다.

현재의 잠정 판단은 **조건부 가능**이다. 첫 API 응답과 문서 표본을 확인한 뒤 이
판단을 갱신한다.
